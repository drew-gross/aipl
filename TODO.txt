Why the formatter isn't already a thin wrapper

The parser consumes decoded token values (StrLit(value, style)) because it only builds an AST — it never reproduces source. The formatter has the opposite obligation: reproduce every token's source spelling byte-for-byte. That's lossy from the value:

- literals_verbatim.aipl: "escaped\tstring\n" must round-trip as those escapes, not as a literal tab + newline. From the decoded value you can't know whether a tab came from \t or a literal tab.
- So for identifiers, operators, numbers, and string/char/template spellings, the Walker slices &self.src[span]. That span-slicing is correct and can't go away.

lex_tokens_and_comments is already a wrapper around lex_aipl (line 2663) — it just projects each LexedToken { kind, span } down to (fmt_kind, span), dropping the value. lex_signatures_and_comments keeps the value instead. The lexer already carries both value and span in one stream; the two entry points each throw one half away.

What you'd actually be changing

Your goal (reindent_block assumes dedented content) needs the raw-block Doc built from the token's de-dented value instead of &self.src[start..end]. Concretely:

1. Have the Walker hold full LexedTokens (or extend FmtTokenKind to carry the literal value), so a """ atom can read its StrLit(dedented_value, TripleQuoted).
2. Build raw_block(...) from that value; reindent_block drops dedent() and the delimiter-parsing, becoming a pure "frame dedented content with delim / reindent_contents(base+4) / base+delim."
3. Retire lex_signatures_and_comments by having the preservation check reuse the unified stream.

The blocker that limits this: interpolated templates

Raw-block reindentation covers both """ strings and ``` templates (see triple_align.aipl). A triple-backtick template's value isn't a single string — it's head/mid/tail **segments around interpolation expressions** ({name}). template_verbatim slices source (line 1496) precisely to preserve the interpolation expressions' spelling. You cannot reconstruct that from the decoded segment values. So:

- The value-feeding trick works for """ strings but not for templates.
- reindent_block must keep handling templates from source text, which is non-dedented → it still needs dedent() for that path.

Net: the dedent is intrinsic to re-indenting a raw block from source spelling. You can relocate it (hoist into the Walker — the "dedent upstream" option, which would also require exposing the dogfooded dedent to aipl-fmt, currently only wired into codegen's engine), but you can't remove it as long as the formatting path works from source — which templates force it to.

Recommendation

- If the real want is just to tidy reindent_block: not worth a lexer refactor. The current content.dedent().reindent_contents(base+4) is honest about what it does, and templates would reintroduce the dedent anyway.
- If the want is architectural unification (one full-token stream feeding both formatting and the preservation check): that's a real, self-contained refactor — maybe a day's work — but note it weakens one safety property. Today the check cross-validates: format via spelling, verify via values, independently. Unifying makes that more circular. And it only lets the """ case (not templates) consume dedented values, so reindent_block stays dual-mode regardless.

My honest read: the dual-stream, span-driven design is well-chosen for a spelling-preserving formatter with interpolated templates — the "operate on parser tokens" model doesn't cleanly fit. If you want, I can prototype the targeted version (raw """ fed from value; reindent_block split so the """ branch is dedent-free while templates keep the source path) so you can see the shape and decide — but I'd want your go-ahead before touching the formatter core.

Reasons dec.aipl uses a cons list:
    1. fits borrows the stack in Rust; AIPL has no references.

    This is the real driver. The Rust fits takes the outer work stack by reference (doc.rs:241):

    fn fits(budget: usize, candidate: &Doc, rest: &[(usize, Mode, &Doc)]) -> bool

    …and then has to rebuild it anyway to push the candidate: rest.iter().map(|(_, m, d)| (*m, *d)).collect() (doc.rs:245) — an O(depth) clone on every group, affordable only because the elements are small Copy tuples of borrowed &Doc.

    AIPL has no borrows; everything passed is an owned/refcounted value. A cons-list tail is shared by pointer, so the AIPL version seeds the lookahead in O(1) with no copy at all (doc.aipl:162):

    aipl
    fits(width - col, WCons(sp, true, inner, rest))

    The list is "the rest of the line" — the same structure the printer holds, reused rather than reconstructed. That's strictly better than what the Rust code does, and it only works because the tail is persistent.

    2. There is no pop builtin.

    crates/aipl-syntax/src/lib.rs:1367 has push, but nothing pops. The only way to shrink an array is a slice, and xs[start..end] is documented as "a fresh heap array copying the element range" (aipl-codegen/src/lib.rs:13511). So while let Some(x) = stack.pop() has no direct translation — emulating it via slicing makes the printer quadratic in document size.

    3. The loop is recursion, so the stack has to be a value.

    go and fits are tail-recursive with the work list as a parameter, where Rust uses while let over a mut local. AIPL does have while (tests/cases/loops/while_loop.aipl), but the functional formulation needs a persistent stack, and WCons gives one where push is a single allocation sharing the existing tail. prepend (doc.aipl:217) is then just a right_fold conses onto that tail, matching Rust's reverse-order push loop.

    Work being a self-referential variant is cheap here because recursive types are boxed with refcounts natively, so the sharing is real rather than deep-copied.

    One caveat on the file's own header comment: it claims the tail-recursive form means it "never recurses on the native stack proportionally to document size." I don't see return_call anywhere in codegen, so guaranteed tail-call elimination doesn't appear to be implemented — that claim may depend on Cranelift happening to optimize the self-call, or it may just be aspirational. The cons-list rationale stands either way; the native-stack part of that comment is worth verifying if you care about it.
