Unifying the `str` and array representations
============================================

Goal: one 24-byte sequence value, `{base, data, len|tag}`, for both. `str24.rs`
already is that for `str`; `arr24.rs` is the array half. The payoff is that a
window into a sequence becomes a *value* rather than an allocation — arrays today
build a 48-byte view block for every slice and every reversal.

Ordering is not a preference. Stage 2 is atomic (see below), and stages 3-6 each
need the wide value to exist, so none of them can land before it.


Stage 1 — the layout, proven on its own                                    [done]
---------------------------------------------------------------------------------
  [x] `arr24.rs`: the value, its reads, windows, reversal, inline, refcounting
  [x] shared verbatim with the AOT runtime, compiles under no_std
  [x] tests: inline boundary, windows share a block, windows compose and clamp,
      reversal and sub-windowing a reversal, a window outliving its source,
      `release` walking the block's count, spare capacity
  [x] asserts the shared half is byte-identical to `str24` so they cannot drift


Stage 2 — widen the value                                           [in progress]
---------------------------------------------------------------------------------
The atomic one, and the reason: the checked-in `dogfood.o` is *called* with
arrays crossing the FFI boundary (`lex_aipl` returns `str[]`, the parser returns
an AST full of arrays), and its compiled code embeds the old layout. A compiler
that disagrees with the artifact cannot parse its own sources to regenerate it.
`str24` solved this by registering both ABIs side by side and moving one entry
point at a time; this needs the same.

  [x] 2a. wide entry points over `arr24`, registered alongside the 8-byte ones
          and not yet called by anything — the scaffolding every later step
          calls into. Additive, so it lands green.
          `aipl_arrw_{len,inline_cap,elem_ptr,slice,reversed,with_cap,inc,dec}`,
          in `arr24.rs`; in codegen's `import_abi` and JIT symbol table so that
          2b-2e are each a change of *caller* only.
          Two notes for 2f: `Ret::Str` is what lowers an array result through a
          leading out pointer (both are 24-byte values written into a caller
          slot) and wants renaming `Ret::Wide`; and `aipl-artifact`'s signature
          table has no `aipl_arrw_*` rows yet, which it needs before any artifact
          references one.
  [x] 2b. the representation knob. `Abi` gained an `arrays: SeqRepr` field —
          `Tagged` (8-byte pointer) or `Wide` (24-byte value) — with `arr_size`
          and `arr_is_composite` beside `str`'s pair, and `abi_elem_size` /
          `abi_is_composite` consulting them for `ConcreteType::Array`.
          `Abi::active` answers `Tagged`, so this step is **inert**: every answer
          is the one it has always been.
          This is the payoff of the `Abi` threading that was kept after `str`
          stopped needing it — its own doc predicted "when the next type gains a
          representation choice it becomes a field here, and nothing downstream
          is re-plumbed", and nothing was.
          `abi_tests` pins both answers, including that a `char[]` is wide under
          *both* (it rides `str`'s representation, not an array block's) and that
          an optional's size tracks its core.

  [ ] 2b-flip. `Abi::active` answers `SeqRepr::Wide`. One line, and the atomic
          moment: it moves struct field offsets, nested-array strides and the
          calling convention together, so it only makes sense with 2c-2e done.
          **Arrays only.** Sets and dicts are array-backed and will want the same
          treatment, but they get their own `SeqRepr` field and their own flip —
          decided, so that each change stays a reviewable size. Until then they
          are sized as a plain word, which is what `abi_elem_size` already does
          for them.
  [x] 2c-0. an artifact records the array ABI its code was compiled for, and an
          engine loaded from it marshals with *that*. Missing from the original
          plan, and the thing that would have made the flip break everything:
          `from_artifact` and `from_prebuilt` took `abi: Abi::active()`, so
          flipping it would have relabelled the checked-in artifact — compiled
          `Tagged` — as `Wide`, and the parser would have read 24-byte arrays as
          8-byte pointers. Now the generator writes `; array-abi <repr>` into the
          header (covered by the source fingerprint, so a representation change
          forces regeneration) and `abi_of_manifest` reads it; no line means
          `Tagged`, an unknown one is refused. Only `Compilation::new`, which
          describes code it just emitted, still uses `Abi::active()`.
  [ ] 2c. array locals, parameters and returns: passed by pointer, returned
          through a leading out pointer (`Ret::Str`'s shape, which already
          exists for exactly this).

          PROBE (2026-10-09, `Abi::active` flipped to `Wide` locally, reverted):
          the compiler survives the flip — 2c-0 is what makes that true, since the
          artifact keeps marshalling `Tagged` — and a plain `[1, 2, 3]` program
          runs. `cases_arrays` went 62 → 49 passing, with **no crashes and no
          compile errors**: 6 wrong `stdout`, 1 `exit code`, 1 `performance`.
          The 13:
            extend_extend, intersperse, list_utils, min_max,
            nested_array_annotation, nested_array_to_str, nested_str_array,
            nonempty, of_sets_and_dicts, push_aliased_array,
            push_push_none_element, starts_ends_with, tuple_windows
          Nearly all are an array *held as an element* — nested arrays, arrays
          of sets/dicts, `tuple_windows`, `intersperse`. `nested_array_to_str`
          prints `[[1, 8], [3], [0, 24, 1]`: codegen strides the outer array at
          24 bytes while the runtime still lays its elements out 8 apart, so
          `8` and `24` are block-header words read as elements.

          What that means for ordering: **2c, 2d and 2e cannot land as separate
          green changes.** The knob flips `arr_size` and `arr_is_composite`
          together, so under `Wide` the *stride* is already 24 while nothing
          below the knob yet stores a 24-byte value. Each step is only checkable
          with the flip on, and with the flip on the tree is red until all three
          are done. So the next change is the flip itself — 2c+2d+2e+2b-flip as
          one unit, driven by this failure list and then the full corpus under
          `Wide` — with 2f (artifact regeneration, delete the 8-byte half)
          following as its own change.
  [ ] 2d. FFI marshalling (`write_ffi_arg`, `read_ffi_*`). Keep the lesson from
          the `str` double-free: a host-built block gets `STATIC_REFCOUNT` so no
          protocol inside the callee can count it down. `ArgBufs::array_block`
          already does this — do not regress it.
  [ ] 2e. codegen's inlined fast paths (`load_arr_len`, `load_array_elem`,
          element stores) read the value's words instead of the block header.
  [ ] 2f. regenerate the dogfood artifact against the wide entry points, then
          delete the 8-byte half: `array_layout.rs`, and the `ArrRepr` arms that
          go with it.

  Intermediate state worth knowing: while 2b-2e are in flight the *blocks* can
  stay exactly as they are. `len` is then carried twice (value and block header),
  the view blocks still exist, and stages 4-6 remove the redundancy one piece at
  a time. That is what keeps each step reviewable.


Stage 3 — inline arrays                                        [blocked on 2]
---------------------------------------------------------------------------------
Elements in the value's own 22 bytes: no allocation, no refcount, exactly as a
short `str` is inline. 22 bytes is 2 `i64`s, 5 `i32`s, 22 `i8`s, or 176
bit-packed `bool`s.

  [ ] 3a. construct one wherever a small array is built: a literal that fits, a
          `map`/`filter` result that fits, a `split` with few parts.
  [ ] 3b. teach element reads and writes the inline case. This is the one that
          bites: the 8-byte attempt SIGSEGV'd because `load_arr_len` and dozens
          of header reads dereference unconditionally, and a value with no block
          has nothing to dereference.
  [ ] 3c. materialize into a block on push/grow past the inline capacity.
  [ ] 3d. decide the boundary per element size, and whether a `drop_fn` element
          type may be inline at all (it needs somewhere to record the count —
          see Stage 6).
  [ ] 3e. bit-packed `bool[]` (`ELEM_BITPACKED`, a stride of 0). `arr24` does not
          handle it yet: `elem_ptr` multiplies by the stride and `spare_capacity`
          divides by it, neither of which is right for bits. `inline_cap` does
          answer for it (22 bytes is 176 bools), so the gap is the accessors.

  Today's `ARR_INLINE_TAG` (8-byte, the empty array over a shared static block)
  is a stand-in for 3 and goes away with 2f. It is not a step toward this: it
  works *because* it points at a block, which is the one thing a real inline
  value cannot do.


Stage 4 — slices as values                                     [blocked on 2]
---------------------------------------------------------------------------------
  [ ] delete the Slice view block and `ARR_SLICE_TAG`; `Arr::slice` is already
      the replacement and allocates nothing
  [ ] remove the `Sliced` arm from every dispatch site (the exhaustive `match`
      will name them)
  [ ] a case proving a slice allocates nothing, the way
      `strings/named_representations.aipl` proves a rope does


Stage 5 — reversed as values                                   [blocked on 2]
---------------------------------------------------------------------------------
  [ ] delete the Rev view block; `Arr::reversed` flips a tag and copies nothing
  [ ] note that reversal keeps a *tag* where a slice does not, because no
      pointer arithmetic reads a run backwards


Stage 6 — the block header, and where unification stops         [blocked on 2]
---------------------------------------------------------------------------------
  [ ] `[drop_fn][init][cap][refcount][elements]`; `len` leaves the block, since
      the value carries it. NOTE: we have static typing so we should be able to
      avoid the drop_fn for primitives like ints/chars/bools that don't have a drop.
  [ ] `init` is the block's own initialized element count, and it is *not* the
      value's `len`: a window's `len` is the window's, so releasing through a
      window would leak the elements outside it. `arr24`'s
      `a_window_releases_every_element_of_its_block` pins this.
      Stage 8 asks whether `init` can be dropped in favour of `cap` — settle that
      before building this header, since it is the same edit either way.
  [ ] `drop_fn` has to stay in the block: `aipl_arr_drop_arr(elems, len)` walks
      a nested array's elements without knowing their element type, so it cannot
      be handed the inner helper by codegen.
  [ ] those two words are the whole of what a `str` buffer does not need. Decide
      whether to say so in `DESIGN_PRINCIPLES.md` or leave it in the two file
      headers.


Stage 7 — delete what the switch leaves behind              [blocked on 2f]
---------------------------------------------------------------------------------
A representation switch leaves its predecessor compiled but unreachable, and the
`str24` switch is the proof: the 8-byte `str` is still in the tree, behind
`#[allow(dead_code)]`, and the AOT runtime reports **39 dead-code warnings** for it
when compiled directly (`rustc --crate-type=staticlib runtime/aipl_runtime.rs`).
Those warnings are the checklist — that is what makes this stage mechanical rather
than archaeological, and it is worth doing for `str` at the same time as for
arrays, since the two switches leave the same kind of residue.

Already identified, from `str`:
  [ ] the retired 8-byte `str` block in `aipl-codegen/src/lib.rs` and in
      `aipl-linker/runtime/aipl_runtime.rs` — both are labelled as retired, so
      the labels are the extent of it
  [ ] its `StrRepr` enum and `str_repr` classifier, and the tag constants
      (`TAG_MASK`, `INLINE_TAG`, `HEAP_TAG`, `VIEW_TAG`, `CONCAT_TAG`)
  [ ] the old FFI `str` path: `build_borrowed_str`, `ArgBufs::str_value`,
      `ArgBuf::Str`, `alloc_dynamic_string`, `free_dynamic_string`,
      `STR_HEADER_SIZE`, the 8-byte `pack_inline`
  [ ] `Ret::Str` → `Ret::Wide`: it is what lowers *any* 24-byte sequence result
      through a leading out pointer, and reads as the wrong name now that an
      array result uses it too
  [ ] `abi_spike.rs` — a spike for the `str` ABI, kept as a regression test for
      the Cranelift lowerings it proved. Confirm that is still what it is, or
      delete it
  [ ] the `builtin_calls` counter table: its `AIPL_*` index constants for the
      `str` entry points are never bumped, because those moved into the shared
      `str24` module without a `count_builtin!`. Either count them or drop the
      rows — today a `--- performance ---` breakdown silently has no `aipl_str_*`
      line
  [ ] `aipl_concat_lazy` / `aipl_concat_mut` / `__aipl_trim_mut`-style aliases
      that now all resolve to one entry point

And what this switch will add:
  [ ] `array_layout.rs` in its entirety, once nothing reads the 8-byte layout
  [ ] `ArrRepr` and its `Heap`/`Reversed`/`Sliced` arms, with the view blocks
  [ ] `ARR_INLINE_TAG` and the shared static empty block — the stand-in for
      stage 3, which exists only because it can point at a block
  [ ] `SeqRepr::Tagged` itself, and the `Abi` field, if arrays end up being the
      last type to have a choice

  Do this as its own change, after 2f is green. Mixing deletion into the switch
  is how a switch stops being reviewable.


Stage 8 — can `init` go away?                                   [decide later]
---------------------------------------------------------------------------------
Stage 6 gives the block an `init` word — its own initialized element count —
because `release` has to drop every element the block owns and the value's `len`
cannot say how many (a window's `len` is the window's). It is the one word that
makes an array block more than a `str` buffer, so it is worth asking whether it is
really needed.

  [ ] Could `cap` serve instead? It is the block's byte capacity, so
      `cap / elem_size` is an upper bound on the elements — and dropping the
      whole capacity would be correct *if* dropping a never-initialized slot were
      valid and a no-op.
  [ ] What would make that true: the element region is zero-filled on allocation,
      and every element drop helper treats an all-zeroes slot as nothing to
      release. That is already true of the shapes that matter — a zeroed `str` is
      `Str::empty()`, a zeroed array is `Arr::empty()`, a zeroed refcounted
      pointer is null, and a zeroed inline composite is a struct of those — and
      `ArgBufs::array_block` already zeroes for a related reason ("a partially
      written inline composite element must read back as zeroes").
  [ ] What to check before believing it:
        - the cost of zeroing. `alloc_zeroed`/`calloc` gets fresh zero pages from
          the OS for a large block, so it may be free where it matters and a
          `memset` only for small ones. Measure, do not assume.
        - whether any element type has a valid all-zeroes value that *does* own
          something. A boxed (recursive) value is a pointer, so zero is null; a
          variant's zero tag is its first case, whose payload would also be
          zeroes. Enumerate rather than reason by example.
        - `cap` is bytes and `elem_size` is not stored in the block, so the
          drop helper would have to be handed the stride, or the count, or stay
          per-element-type. That may just move `init`'s cost rather than remove
          it.
  [ ] If it works, Stage 6's header is `[drop_fn][cap][refcount]` and the only
      difference from a `str` buffer is `drop_fn` — which is a much better place
      for the unification to stop.

  Not now. Decide after 2f, when the block layout is the thing being changed
  anyway.


Open questions
---------------------------------------------------------------------------------
  [ ] Is one `Seq` type better than two that match shape? The tags differ (`str`
      has a rope, arrays have a reversal) and the element stride is compile-time
      for arrays and always 1 for `str`. Sharing the *type* may cost more than
      sharing the layout, which is already enforced by a test.
  [ ] `char[]` already rides `str`'s representation, so it gets inline for free
      today. After Stage 3 it has two possible answers — check nothing depends
      on which.
