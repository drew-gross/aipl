The AIPL implementation of the measure builtin. Monomorphization registers this under the canonical name __builtin_measure (see AIPL_BUILTIN_SOURCES in lib.rs), so a user's measure("label", input, |x| f(x)) resolves through the ordinary generic / higher-order machinery — the in-file name measure is only for this file's own tests, which read exactly like user code.

It runs f(input) once inside a counting window and hands back what that cost. The window is the three internal builtins it is made of: measure_begin opens it, measure_end closes it, and measure_read reads a counter of the closed window. Between them, measure_consume releases the result — inside the window, because freeing it is part of what the work costs, and as a use the optimizer cannot remove, because a pure call whose result nobody reads is dropped altogether, and a measurement of nothing is not a measurement.

All of them carry the internal !measure effect, and so does this function. That is the whole of why it can only be called from a .performance block: the block declares !measure and nothing else, and no other function can.

No lint. Nothing is being reimplemented: there is no longhand to match.

measure fn 

pub fn measure<T: any, R: any>(label: str, input: T, f: (T) -> R) !measure -> Measurement

What f(input) cost, counted from just before it starts to just after its result is released: the heap allocations it made, the bytes those asked for, the most heap that was live at once (counted from what was live when it began), and the CLIF instructions it executed. label names the measurement in reports; it is not a key — two measurements may share one in a block — but a repeated literal label is refused at compile time, since a report could not tell them apart.

The counts are exact and repeatable, so a claim about them can be an equality, and when the code being measured is small it should be: the number is the claim, and few commits touch small code, so it seldom needs updating — when it does, that is the commit worth looking at. Code that many commits touch would make an exact count churn with each of them; state a comparison between two measurements instead (a.instructions == b.instructions), or a bound. The counts include a small constant for the call and release themselves (5 instructions), the same on every measurement, so it cancels in a comparison and is part of an exact count.

The input is built outside the window and handed in so that building it is not what is measured, and f is called with it exactly once. Callable only in a .performance block.
