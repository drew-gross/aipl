The AIPL implementation of the map_reduce builtin. The loader names this function by the canonical name __builtin_map_reduce (see aipl_syntax::aipl_builtins), so a user's xs.map_reduce(f, step) resolves through the ordinary generic / higher-order machinery — the in-file name is only for this file's own tests, which read exactly like user code.

It is what xs.map(f).<reduction>() means, in one pass and with no mapped array built: map would allocate every f(x) for the reduction to walk once and drop. The reduction is the step, which combines what has been reduced so far with the next mapped element — min for minimum, max for maximum. Written by the compiler's operation-fusion pass for those chains (see chain_fusions in aipl-mono, and Callee::reduction_step, where the reductions are named); also callable directly.

map_reduce fn 

pub fn map_reduce<T: any, U: any>(self: T[], f: (T) -> U, step: (U, U) -> U) -> U?

f applied to each element, left to right, combined with step as it goes: for [a, b, c], some(step(step(f(a), f(b)), f(c))). The first mapped element seeds the result, so step is never called on fewer than two; an empty receiver is none, and one element is some(f(that element)).

f runs once per element, in order, interleaved with step rather than before all of them — which no one can tell apart unless step does something, and a reduction's step does not.
