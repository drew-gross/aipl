format_source, the formatter's top-level pipeline.

The sequence is: split off the trailing --- section --- blocks, strip trailing whitespace from what's left, parse it with the real parser, lay it out, normalize to exactly one trailing newline, verify the output holds the same tokens as the input, then re-attach the sections verbatim.

Parsing comes before layout on purpose: the parser's errors are the good ones, and anything it accepts the walker must handle, so a malformed program fails with the parser's message rather than whatever the walker makes of it. The token check comes after and is the safety net: the output must carry exactly the input's tokens and comments, or it is refused rather than emitted — a formatter bug must never corrupt code.

This used to be two AIPL entries with the parse and the token check between them in Rust, from before the parser was itself dogfooded. Now the whole pipeline runs in-engine and Rust's format_source is one FFI call.

format_source fn 

pub fn format_source(src: str, width: u64) -> str!FmtError

Format AIPL source to the canonical style, at width. The output always ends in exactly one newline (an empty program formats to just that). The input's trailing --- section --- blocks are preserved byte-for-byte — they follow that newline, and whatever they end with is theirs; trailing whitespace in the source portion is removed (the language rejects it, so fixing it can't change an accepted program's meaning).

TokenFingerprint struct 

struct TokenFingerprint

A lexed source reduced to what a reformat must preserve: every non-import token in order, the import statements as a sorted multiset, and the comments as one too. Two sources with equal fingerprints hold the same code.

A token counts as its value (token_value), so the formatter's value-preserving whitespace edits inside a """ block are not flagged while any change to a literal's value is.

Three things a reformat is allowed to change, and each is why a part is shaped the way it is:

  • Imports are hoisted and sorted, both the statements and the names inside

one. So each statement collapses to its own tokens sorted and joined (import_signature) and the statements are then sorted among themselves — reordering is invisible, losing or changing a name is not.

  • A trailing comma is normalized (dropped when a list renders flat, added

when it breaks), and a variant's leading | is the same normalization at the other end. Both are layout, so is_layout drops them before anything else — which also excludes the | between match-pattern alternatives.

  • Comments move with the construct they are glued to, which can reorder

them against the tokens, so they are their own sorted multiset rather than part of rest.

Everything else is positional: rest catches a token the layout moved, not just one it lost.

verify_same_tokens fn 

fn verify_same_tokens(input: str, output: str) -> ()!FmtError

Refuse unless output holds exactly input's tokens and comments — exactly as TokenFingerprint defines it, which is where the three things a reformat is allowed to change are spelled out.

The three parts are reported separately so the message names what moved: a reordered statement is an import-hoisting bug, a reordered token is a layout bug, and they want different reading.

collapse_templates fn 

fn collapse_templates(values: str[]) -> str[]

An interpolation-free template folded to the one string value it is.

`a` and "a" are the same program — the parser lowers a template with no interpolations to a plain string, and requote moves a literal between the two spellings to save escapes. They are not the same tokens, though: one is a run of three and the other is one, so a token-by-token comparison would call a legal respelling a formatter bug. Folding the run is what lets the check stay token-based everywhere else.
