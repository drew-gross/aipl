The destructure lint: a name that a pattern could take apart, because the value itself is never used — only its fields are. Three places bind such a name, and the argument is the same for each:

fn f(p: Point) { .. p.x .. p.y .. }        fn f(Point { x, y }) { .. x .. y .. }
let p = pos_of(i); .. p.line .. p.col      let Pos { line, col } = pos_of(i);
for (let Dot(pos) : xs) { pos.line }       for (let Dot(Pos { line }) : xs) { line }
  • A parameter, whose type is in the signature, so the advice names the struct.
  • A let of a plain name, with or without an annotation. A mut binding is a

different question — whether it should be mut at all — and answering it here would advise a rewrite that changes more than the spelling.

  • A slot of a pattern: the payload of a case, a position of a tuple, bound by a

parameter, a let or a for. The slot's type is not written anywhere in the file, so the advice leaves it as a placeholder.

The reader of fn f(Point { x, y }) or let P { line, col } = pos_of(i); knows the fields are the whole story; with a name they have to scan the rest of the body to find out whether it is also passed somewhere, compared, or returned.

The name is taken apart in one of two ways, and either is advised:

  • Only fields are read (p.x, p.y). One bare mention is enough to stay

quiet, because a pattern cannot reproduce it — the value itself is gone, only its fields survive. That covers the obvious escapes (f(p), p == q, a trailing p) without special-casing any of them.

  • The name's one use opens a destructuring let (let Point { x, y } = p;

right under the binding): the pattern is the one the author wrote, one step late, and moves up unchanged.

A pattern binds one name per field, so it is only available when each of those names would mean one thing in the function. Two conditions take the lint out, and between them they are most of what it would otherwise flag (field_uses holds the rules):

  • The name is already spoken for. let b = w.bump(); reading b.text and

b.w cannot become let Bump { text, w } = w.bump(); where a w is in scope: the new binding shadows it and every later mention of the old one silently changes meaning. The binding's own name does not count, being the one going away.

  • The field is read off more than one value. Three lets binding the same

struct in one block are told apart by their names (plain.cleaned, empty.cleaned); destructuring them all binds cleaned three times and the distinction the names carried is gone. Reads inside a let's own value are the exception: it is evaluated before the pattern binds anything.

What is left alone:

  • self. Method-call syntax is defined by the receiver being named self, so

its pattern is the named form self: Span { start, end }, not the Span { start, end } this lint's advice spells.

  • A parameter already destructured, whose pattern the author wrote.
  • A keyword parameter. Its name is the call-site spelling (f(sep = ", ")),

so destructuring it would break every caller.

  • mut and variadic parameters. A mut receiver is written through rather

than read, and a variadic parameter's type is a sequence.

  • Anything but a plain named type as a parameter's type. A generic instance is

a template until monomorphization and a parameter has no value to infer arguments from, so Box { v } has nothing to bind; arrays, optionals and primitives have no fields to name.

  • A value built on the line. Taking apart P { a: 1 } restates the type name

and re-lists the fields that literal just set.

  • A name the parser made (__iset1$6), which the author did not write and

cannot put an #[allow] on, and _, which binds nothing.
