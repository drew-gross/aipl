AIPL

crates/aipl-codegen/src/lexer.aipl

A small library for building lexers. lex turns source text into a flat Token[], driven by an ordered TokenRule[] describing the language being lexed. Each rule pairs a caller-chosen kind label with a Matcher — a data-only description of one token shape (a char-class run, a list of fixed spellings, a delimited literal, ...) — so a rule set is plain data and one lex serves many languages; see the JSON and AIPL-flavored rule sets in the tests. At each position the first rule whose matcher matches wins, so order is priority: put keywords before identifiers, floats before ints. Whitespace is an ordinary rule marked skip: true — matched and consumed, but producing nothing. Rules marked trivia: true (comments, lint markers) are consumed the same way but recorded in the result's trivia side-channel, so a formatter or lint pass can find them without them cluttering the token stream. Lexing can fail: a byte no rule matches, or a matcher that matches invalid input outright (an unterminated Delimited token), aborts the lex with a LexError — a message plus the span of the offending source.

SpanStr struct 

struct SpanStr

Matched text together with where it was matched: the two halves every consumer of a token needs, carried in one value so they cannot be separated.

A SpanStr is built by span_str and nothing else, which is what makes its one invariant hold: text is exactly src[span] for the source it was sliced from. Consumers rely on that in both directions — a diagnostic renders span against the source it already has, and a parser reads text without needing the source at all.

It is a plain struct, not a language feature: str alone cannot carry the offset (a str is text, and two equal strings from different places are equal), so the span rides alongside. That costs 16 bytes over a bare str, and buys every function downstream one parameter instead of two.

span_str fn 

pub fn span_str(src: str, at: Span) -> SpanStr

src[at] paired with at — the only way a SpanStr is made, so its text-matches-span invariant holds by construction. Slicing clamps, so an out-of-range or inverted at yields the empty text rather than failing; span is kept verbatim either way, since it is what a caret block underlines.

Token struct 

struct Token<K: any>

What a token is: its kind — a caller-defined value carrying whatever the matched token means, produced by the rule's emit (see Emit) — and its text, the raw source it covers plus the span it covers (see SpanStr). Token is generic over the kind type K, so a language pins K to its own variant whose arms are the token kinds, each carrying that kind's content (Int(i64), Str(str), a bare Plus, …) — rather than a stringly-typed label plus a separate value.

The text is carried rather than recovered by slicing (src[t.span], as it used to be) so that holding a token is enough: a parser does not thread the source alongside its token list just to read a token back.

Emit variant 

variant Emit<K: any>

How a rule turns its matched token into a kind K: a fixed set of options.

Four of the five are handed the token's content string — the delimiter-stripped text for a string matcher (Delimited/Between/Nested), or the raw matched text for everything else (identifiers, whose text is their content, and numeric Int/Float runs, whose emit parses the digits itself). The two never overlap — a matcher either strips delimiters or has none — so one notion serves both, always handing over the meaningful content.

  • Bare(K)

    A finished kind for a valueless token: punctuation, an operator.

  • Of((str) -> K)

    Applies a constructor to the token's content string.

  • Try((str) -> K!str)

    Of's fallible sibling: the function returns K!str — a kind, or an error message. Interpreting a match can fail (a numeric literal that overflows i64, a single-quoted string that isn't exactly one char), and on err(msg) the library pairs the message with the token's whole span to build a LexError (see apply_emit). The token span is the right location for a whole-token verdict like overflow; a matcher-level, byte-precise error (an unterminated string, an unknown escape) still comes from scanning, not the emit.

LexError struct 

struct LexError

Why a lex failed: what went wrong, and the span of the offending source (absolute into the lexed string — slice it to show the offender).

Matcher variant 

variant Matcher

One token shape, as plain data. Char classes and fixed spellings are both spelled as strings (class membership via contains, a spelling matched whole); none of them ever match empty input, so lex always makes progress.

Every token has a content string, and that is what its rule's emit is handed (see token_content): the raw matched text, except for the three matchers that bracket their content, which strip their delimiters first. Delimited strips to the contents un-decoded (the rule's emit decodes — escape handling is the caller's, not the library's); Between/Nested strip to the contents verbatim (a raw string's de-denting is the caller's post-pass). Everything else — identifiers, punctuation, keywords, the Int/Float digit runs, every trivia record — is its own text, which an Of emit interprets. That is why a numeric literal's parsing is the rule's emit's job, via the int_parse builtin or its own. The library provides no string-escape decoder: what a \X means is a language's own policy, so a consumer's emit decodes with its own (e.g. lex_aipl.aipl's unescape, mapping \n/\t/\r to control chars and any other \X to X itself). A char literal is likewise not a matcher: a consumer lexes it as a single-quoted Delimited string and enforces the one-char shape in a Try emit (see lex_aipl.aipl's char_lit_emit).

  • CharRun(cont: #{char}, first: #{char} = cont)

    A maximal run of chars in cont. first restricts what may open the run and defaults to cont, so the usual shape — one class for the whole token — is a single argument (CharRun(digits), and whitespace runs), and only a narrower opener is worth naming (CharRun(alnum, first = alpha): an identifier may not start with a digit).

  • OneChar(#{char})

    Exactly one char, any of chars. Single-character punctuation, where one rule stands for a whole class of one-char tokens (OneChar("()[],;")) instead of an Exact rule apiece. It is the direct concept a CharRun cannot state: a run needs something to continue with, so "exactly one" would have to be spelled as a run that can never extend.

  • Exact(str)

    The given spelling, verbatim. Punctuation and operators — one spelling per rule; when spellings share a prefix, order the rules longest first (== before =), since rule order is the priority mechanism (a single rule matching a set, with its own longest-wins, would duplicate that ordering as a second mechanism).

  • Keyword(str, #{char})

    Like Exact, but the spelling only matches when the char after it is absent or outside boundary (the identifier continue class) — so a keyword rule placed before the identifier rule claims if without biting the front off iffy. One spelling per rule, as with Exact; a shared prefix (in/int) is resolved by the boundary check, not rule order, so order among keyword rules doesn't matter.

  • Delimited(#{char}, escaped: #{char} = #{})

    A char in delims opens the token, which runs to just past the next occurrence of the same char. escapes is the set of chars that may follow a backslash inside the token: \ plus an allowed char is content (in particular an escaped delimiter does not close), \ plus anything else is a lex error, and #{} turns escape handling off entirely (a backslash is ordinary content). A token still open at the end of the source is a lex error. String literals. escapes governs scanning only — the token's value is the delimiter-stripped text left un-decoded, so the rule's emit decides what escapes mean, with its own decoder (the library provides none — escape semantics are the language's).

  • Between(str, str)

    The open spelling opens the token, which runs to just past the next full occurrence of the close spelling. Unlike Delimited, open and close are multi-char and may differ, and the scan matches the whole close — so a partial close inside (a lone " or "" under a """ close) is ordinary content. Contents are verbatim (no escape processing), which is what raw strings """...""" and non-nesting block comments /* ... */ want. Both spellings must be non-empty. A token still open at the end of the source is a lex error.

  • Nested(str, str)

    Like Between, but depth-tracked — each further open inside raises the nesting depth and the matching close lowers it, so the token ends only at the close that balances the outermost open. Rust-style nesting block comments /* ... /* ... */ ... */. open and close must be distinct (a delimiter can't both open and close a level) and non-empty. A token still open (depth > 0) at the end of the source is a lex error.

  • UpToAny(stops: str[], escapes: #{char}, refuse_unknown_escape: bool = true)

    A maximal run of text holding none of the stops spellings, with \X escapes consumed as a unit and checked against escapes exactly as Delimited does (#{} turns escaping off, leaving the run verbatim).

    The complement of the bracketing matchers: where they are told what encloses a token, this one is told what ends it and consumes up to there without consuming the terminator. That is the shape a mode wants — inside a template, text runs until the closing delimiter or the { that opens an interpolation, and each of those is a token of its own belonging to another rule.

    The stops are spellings rather than chars so a multi-char terminator works: a run inside a ``` template stops at the full ``` and a lone backtick stays content, the same distinction Between draws.

    Reaching the end of the source is a match, not an error: an unclosed construct is the mode's to report (see Transition), and this matcher has no idea what opened the one it is scanning inside of. Like every matcher it declines rather than matching empty, so a stop spelling at the cursor is length 0 — which is exactly right: the rule that matches the terminator is the one that should win there, so order it first.

    • stops: str[]
    • escapes: #{char}
    • refuse_unknown_escape: bool = true

      Whether a \X whose X is not in escapes is a hard error, as in Delimited, or ordinary content. Content is what a verbatim scan wants: a raw template decodes \{/\} so a brace can be written without opening an interpolation, and holds every other backslash as written — so it lists those two and refuses nothing.

  • ToEol(str)

    The marker spelling, then everything up to (not including) the next newline. Line comments — usually skip: true.

  • ToEolUnless(marker: str, blocked: #{char})

    marker, then everything up to (not including) the next newline — but only when the character right after marker is not in blocked. Line comments whose marker is also the start of something else: AIPL's # leads a doc comment, and also a set/dict literal (#{..}), an ordered set (#>{..} / #<{..}) and the #[allow] lint marker, so ToEolUnless("#", "{[<>") claims the comment and leaves the others to the rules that want them.

    The marker alone at end of line still matches — an empty doc line has no following character to block it, and writing one as marker plus a space is not open to a language that forbids trailing whitespace.

  • Float

    A digit run that extends past a fraction (. plus at least one digit) and/or an exponent (e/E, an optional sign, at least one digit), JSON style. A bare digit run does not match — put a Float rule ahead of the int rule and each number lexes as the right one.

  • Int

    A decimal digit run with an optional leading - — a distinct matcher because a number is not an identifier, but (like Float) it carries no computed value: its text is left unparsed, so the rule pairs it with an Of/Try emit that parses the digits (and any sign) itself (via the int_parse builtin, or its own scanner). Parsing — base, digit separators, and what overflow means — is the caller's, not the library's. The - is consumed only when a digit immediately follows it, so - 5/-x (a space or a letter after the -) don't match and are left for a - operator rule. Rule order alone then decides the reading: Int before a - operator makes -5 a signed literal (and a - 5 still subtraction, since the - 5 there has a space); the operator before Int makes every - the operator and Int unsigned. Scanning the sign into the token is also what lets the emit reach the full signed range — an i64's -9223372036854775808 overflows as a positive literal, so it's only expressible with the - and digits together.

Transition variant 

variant Transition

What matching a rule does to the lexer's mode stack.

A rule set is otherwise context-free at the token level: the rules are tried in order at every position, so the same bytes always lex the same way. That is what keeps a rule set plain data — and it is not enough for a language where the same bytes mean different things in different places, which is any language with string interpolation: in `a{x}b` the b is template text and the x is an identifier, and only what came before tells them apart.

A mode is a named subset of the rules, named by a u64 the caller assigns. The lexer is always in one and only its rules are tried, so a rule can be invisible outside the context it belongs to. Push enters a mode and Pop leaves it.

The stack is what makes contexts nest. A single "current mode" could say where the lexer is but not what it returns to when the context ends; a stack answers both, at any depth. { inside a template pushes, and the } that balances it pops back into the template — and a template inside that interpolation simply pushes again. Nothing here counts depth: the stack is the depth.

Pop at the base mode stays at the base rather than running off the bottom. A stray closer is a syntax error for a parser to report against a token, not a lexical one — the lexer's job is to hand over the tokens.

  • Stay
  • Push(i64)
  • Pop

ModeFrame struct 

struct ModeFrame

One entry of the mode stack: the mode, where the token that pushed it started, and that rule's unterminated message. The span and the message are carried so that a mode still open at the end of the source is reported against its opener — which is where a reader has to go to fix it — rather than against the whole remaining source.

TokenRule struct 

struct TokenRule<K: any>

One prioritized entry of a rule set: the shape to match, how to turn a match into a kind (emit), and what becomes of its matches. A plain rule emits a token; skip: true consumes matches silently (whitespace); trivia: true consumes them but records each in the result's trivia side-channel — for matches a later pass wants located but not parsed, like comments (a formatter re-attaches them) or lint markers (#[allow]). Set at most one of the two flags (skip wins when both are set). Generic over the kind type K — every rule of one set builds the same K. unterminated overrides the message used when this rule's token runs off the end of the source (a Delimited/Between/Nested scan that never closes), or that this rule's mode is still open there (see Transition). Empty means "use the built-in default" (a generic "unterminated delimited token") — so a rule can name its token in the diagnostic ("unterminated string literal") without every rule having to.

mode and go are the rule's place in, and effect on, the lexer's mode stack — see Transition. A rule set that mentions neither is entirely in the base mode, which is how every rule set that predates modes keeps working.

scope is the TextMate scope a syntax highlighter should paint this rule's matches — "keyword.control.aipl", "string.quoted.double.aipl". lex ignores it entirely: it is carried here so that one rule set describes a language's lexical structure once, for the lexer and the highlighter both (highlight.aipl generates the second from it), rather than the two drifting apart as separate descriptions. Empty means "not highlighted", which is what a skip rule wants. The same hint on the syntactic half is Production.scope in grammar.aipl.

LexResult struct 

struct LexResult<K: any>

What lex returns: the emitted tokens, and the trivia side-channel — the recorded matches of every trivia: true rule, in source order. Silent skip matches appear in neither.

keep_skipped fn 

pub fn keep_skipped<K: any>(self: TokenRule<K>[]) -> TokenRule<K>[]

self with every skip rule turned into a trivia rule: nothing is dropped, so every byte of a lexed source is accounted for by some token or trivia record.

A compiler's rule set skips whitespace outright — it has no use for it, and recording it would cost every consumer something only one of them wants. A lossless consumer has the opposite need: a parser building a concrete syntax tree, or a formatter reproducing its input, must be able to put every byte back. Both read the one rule set through this, rather than the language keeping two of them.

StepResult struct 

struct StepResult<K: any>

One lexing step's outcome: the token the winning rule produced, or the trivia it recorded instead, plus the position just past the consumed text. end staying at the step's start means no rule matched.

At most one of each, and never both. A rule is a token rule or a trivia rule, and a skip rule is neither — so exactly one of these arrays holds a token, or neither does. They are arrays rather than optionals because a struct field cannot be an optional struct: the checker admits an optional only of a scalar, a str, an array or a recursive type. An array of nought-or-one is how the language spells "maybe a token" here.

They were arrays for a stronger reason until recently: Matcher::Template emitted a whole head/interpolation/tail run from a single step, and it was the only matcher that ever emitted more than one token. Modes replaced it, and each piece of a template is now its own step.

ScopeSpan struct 

struct ScopeSpan

Lexes self into a LexResult: the flat token list, plus the trivia side-channel, as described by the ordered rules. At each position the first rule whose matcher matches claims the token (so order is priority — keywords before identifiers, floats before ints); a skip: true rule consumes its match without producing anything (whitespace), and a trivia: true rule records its matches in the side-channel instead of the token stream (comments, lint markers). Lexing fails with an err — a LexError carrying a message and the offending span — when a byte matches no rule or a matcher sees invalid input outright (an unterminated Delimited token). One token's span and the scope its rule declares — the highlighting side-channel. TokenRule.scope exists so that one rule set describes a language's lexical structure once, for the lexer and the highlighter both; this is that hint read per token rather than per rule.

LexAll struct 

struct LexAll<K: any>

Everything one lex produces: the tokens and trivia a consumer wants, and the scope of every token for a consumer that paints. Two views of one drive loop, so neither can disagree with the other about what matched where.

transition fn 

fn transition(push: i64, pop: bool) -> Transition

A rule's push/pop pair read as the one decision it is. The flags are a pair because a struct field's default must be a literal, so neither a constructor nor an optional variant can sit on TokenRule; classifying them here means the stack is driven by an exhaustive match on three cases rather than by two booleans checked in the right order at each site.

delimited_len fn 

fn delimited_len(self: str, at: u64, delims: #{char}, escapes: #{char}, msg: str) -> u64!LexError

Delimited: a delims char opens the token, which spans to just past the next occurrence of the same char. ok(0) when the first char isn't a delimiter. With a non-empty escapes set, a backslash escapes its next char: an allowed char is content (an escaped delimiter doesn't close), a disallowed one is a hard error, and so is a backslash with nothing after it — the end of the source cut the escape off. A token still open at the end of the source is a hard error (at is the token's absolute start, so error spans land in the real source).

between_len fn 

fn between_len(self: str, at: u64, open: str, close: str, msg: str) -> u64!LexError

Between: the open spelling opens the token, which runs to just past the next full occurrence of close. ok(0) when self doesn't start with open. The close scan starts past the open and matches the whole close spelling, so a partial close inside (a lone "/"" under a """ close) is content, not a terminator, and open/close may be multi-char and differ. No escapes — contents are verbatim. A token still open at the end of the source is a hard error (at places the span in the real source).

up_to_any_len fn 

fn up_to_any_len(self: str, at: u64, stops: str[], escapes: #{char}, refuse_unknown_escape: bool) -> u64!LexError

UpToAny: the length of the run before the first of stops, or the whole of self when none of them appears. \X escapes are consumed as a unit and validated as in delimited_len, so an escaped terminator does not end the run and an unknown or cut-off escape is the same hard error there.

0 when a stop spelling sits at the cursor — a decline, like every other matcher, which hands the position to the rule that matches the terminator.

nested_len fn 

fn nested_len(self: str, at: u64, open: str, close: str, msg: str) -> u64!LexError

Nested: the depth-tracked Between. The open spelling opens the token at depth 1; each further open raises the depth and each close lowers it, so the token ends just past the close that returns the depth to 0. ok(0) when self doesn't start with open. open is tested before close so an overlap can't misclassify, but the two must be distinct for nesting to mean anything. No escapes — contents are verbatim. Still open (depth > 0) at the end of the source is a hard error (at places the span in the real source).

The end of the number whose integer part ends at int_end: extends past a fraction (. then at least one digit), then past an exponent (e or E, an optional sign, then at least one digit). Either part may be absent; int_end comes back unchanged when neither matches.

float_len fn 

fn float_len(self: str) -> u64

Float: a digit run that extends past a fraction and/or exponent. A bare digit run is 0 (no match) — it belongs to the int rule.

int_len fn 

fn int_len(self: str) -> u64

Int: the length of an optional leading - then a digit run. 0 (no match) when there's no digit run — including a - not immediately followed by a digit (a - before a space or a letter is left for a - operator rule, so - 5/-x don't match). The content string a token of matcher m is built from: its matched text (src[at..at+n], delimiters included), with the delimiters taken off by the three matchers that bracket their content — see the table on Matcher. Everything else is its own text, and its rule's emit interprets it.

Build a token's kind by applying the rule's emit to its content string — what token_content made of the matched text. Bare ignores it; Of applies its constructor; Try does too but may fail with a message (paired with the token span to make a LexError).

step_result fn

A simple (single-token) matcher's outcome: a decline when the matched length n is 0, otherwise n chars consumed producing the rule's one token — recorded as trivia for a trivia rule, or nothing at all for a skip rule. lex_step fn 

fn lex_step<K: any>(src: str, at: u64, rules: TokenRule<K>[], mode: i64) -> StepResult<K>!LexError

One lexing step at absolute position at: tries each rule of mode in order (first match wins) and returns the winning rule's outcome — see StepResult. Each arm computes how far its matcher reaches (0 for no match — no matcher matches empty input, so a nonzero length always means progress) and wraps it via step_result.

A rule of another mode is passed over rather than filtered out up front: the check is one comparison inside the loop that already runs, where filtering would build a new array at every position of every lex.
