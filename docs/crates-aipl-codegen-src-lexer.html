TokenValue variant 

variant TokenValue

What a token carries beyond its span: the processed *value* of the matched text, computed at lex time by the matcher that claimed it (see each matcher's doc). StrVal holds delimiter-stripped, *un-decoded* text (strings, raw strings, template segments) — the library strips the delimiters but leaves escapes verbatim for the rule's emit to decode with its own decoder (escape meaning is a language's policy, not the library's). Everything a rule can recover by slicing its span — identifiers, punctuation, keywords, comments, and the Int/Float numeric runs (whose *parsing* is the rule's emit's job, via the int_parse builtin or its own) — carries NoValue. (A char literal is not a library concern: a consumer that wants one lexes it as a single-quoted Delimited string and validates the one-char shape in its emit — see lex_aipl.aipl.)

  • StrVal(str)

SpanStr struct 

struct SpanStr

Matched text together with where it was matched: the two halves every consumer of a token needs, carried in one value so they cannot be separated.

A SpanStr is built by span_str and nothing else, which is what makes its one invariant hold: **text is exactly src[span]** for the source it was sliced from. Consumers rely on that in both directions — a diagnostic renders span against the source it already has, and a parser reads text without needing the source at all.

It is a plain struct, not a language feature: str alone cannot carry the offset (a str is text, and two equal strings from different places are equal), so the span rides alongside. That costs 16 bytes over a bare str, and buys every function downstream one parameter instead of two.

span_str fn 

pub fn span_str(src: str, at: Span) -> SpanStr

src[at] paired with at — the only way a SpanStr is made, so its text-matches-span invariant holds by construction. Slicing clamps, so an out-of-range or inverted at yields the empty text rather than failing; span is kept verbatim either way, since it is what a caret block underlines.

Token struct 

struct Token<K: any>

What a token is: its kind — a caller-defined value carrying whatever the matched token means, produced by the rule's emit (see Emit) — and its text, the raw source it covers plus the span it covers (see SpanStr). Token is generic over the kind type K, so a language pins K to its own variant whose arms *are* the token kinds, each carrying that kind's content (Int(i64), Str(str), a bare Plus, …) — rather than a stringly-typed label plus a separate value.

The text is carried rather than recovered by slicing (src[t.span], as it used to be) so that holding a token is enough: a parser does not thread the source alongside its token list just to read a token back.

Emit variant 

variant Emit<K: any>

How a rule turns its matched token into a kind K: a fixed set of options.

Four of the five are handed the token's *content string* — the delimiter-stripped text for a string matcher (Delimited/Between/Nested), or the raw matched text for everything else (identifiers, whose text is their content, and numeric Int/Float runs, whose emit parses the digits itself). The two never overlap — a matcher either strips delimiters or has none — so one notion serves both, always handing over the meaningful content.

  • Bare(K)
  • Of((str) -> K)
  • OfSeg((str, Seg) -> K)
  • Try((str) -> K!str)
  • TrySeg((str, Seg) -> K!str)

Matcher variant 

variant Matcher

One token shape, as plain data. Char classes and fixed spellings are both spelled as strings (class membership via contains, a spelling matched whole); none of them ever match empty input, so lex always makes progress.

Tokens carry values (see TokenValue), computed by the claiming matcher: Delimited a StrVal of the delimiter-stripped contents, *un-decoded* (the rule's emit decodes — escape handling is the caller's, not the library's); Between/Nested a verbatim StrVal of the contents (a raw string's de-denting is the caller's post-pass). Template (its segments), Int/Float (their digit text), and everything else — plus every trivia record — carry NoValue, so an Of emit recovers the raw matched text and interprets it. The library provides no string-escape decoder: what a \X means is a language's own policy, so a consumer's emit decodes with its own (e.g. lex_aipl.aipl's unescape, mapping \n/\t/\r to control chars and any other \X to X itself). A char literal is likewise not a matcher: a consumer lexes it as a single-quoted Delimited string and enforces the one-char shape in a Try emit (see lex_aipl.aipl's char_lit_emit).

TokenRule struct 

struct TokenRule<K: any>

One prioritized entry of a rule set: the shape to match, how to turn a match into a kind (emit), and what becomes of its matches. A plain rule emits a token; skip: true consumes matches silently (whitespace); trivia: true consumes them but records each in the result's trivia side-channel — for matches a later pass wants located but not parsed, like comments (a formatter re-attaches them) or lint markers (#[allow]). Set at most one of the two flags (skip wins when both are set). Generic over the kind type K — every rule of one set builds the same K. unterminated overrides the message used when this rule's token runs off the end of the source (a Delimited/Between/Nested/Template scan that never closes). Empty means "use the matcher's built-in default" (a generic "unterminated delimited token" / "unterminated template literal") — so a rule can name its token in the diagnostic ("unterminated string literal") without every rule having to.

scope is the TextMate scope a syntax highlighter should paint this rule's matches — "keyword.control.aipl", "string.quoted.double.aipl". lex ignores it entirely: it is carried here so that one rule set describes a language's lexical structure *once*, for the lexer and the highlighter both (highlight.aipl generates the second from it), rather than the two drifting apart as separate descriptions. Empty means "not highlighted", which is what a skip rule wants. The same hint on the syntactic half is Production.scope in grammar.aipl.

LexResult struct 

struct LexResult<K: any>

What lex returns: the emitted tokens, and the trivia side-channel — the recorded matches of every trivia: true rule, in source order. Silent skip matches appear in neither.

keep_skipped fn 

pub fn keep_skipped<K: any>(self: TokenRule<K>[]) -> TokenRule<K>[]

self with every skip rule turned into a trivia rule: nothing is dropped, so every byte of a lexed source is accounted for by some token or trivia record.

A compiler's rule set skips whitespace outright — it has no use for it, and recording it would cost every consumer something only one of them wants. A *lossless* consumer has the opposite need: a parser building a concrete syntax tree, or a formatter reproducing its input, must be able to put every byte back. Both read the one rule set through this, rather than the language keeping two of them.

StepResult struct 

struct StepResult<K: any>

One lexing step's outcome: the token(s) the winning rule produced — one usually, none for a skip rule, a whole head/expr/middle/tail run for a Template — any trivia recorded along the way, and the position just past the consumed text. end staying at the step's start means no rule matched.

lex fn 

pub fn lex<K: any>(self: str, rules: TokenRule<K>[]) -> LexResult<K>!LexError

Lexes self into a LexResult: the flat token list, plus the trivia side-channel, as described by the ordered rules. At each position the first rule whose matcher matches claims the token (so order is priority — keywords before identifiers, floats before ints); a skip: true rule consumes its match without producing anything (whitespace), and a trivia: true rule records its matches in the side-channel instead of the token stream (comments, lint markers). A Template rule emits several tokens per literal — head/middle/tail segments around the tokens of each {...} interpolation, which are lexed by this same rule set. Lexing fails with an err — a LexError carrying a message and the offending span — when a byte matches no rule or a matcher sees invalid input outright (an unterminated Delimited token).

Keyword: the length of spelling when it prefixes self, but only when the char after it is absent (end of source) or outside boundary — a keyword must not end in the middle of an identifier. 0 when it doesn't match (or the char after is a boundary char, as in iffy for if).

delimited_len fn 

fn delimited_len(self: str, at: u64, delims: str, escapes: str, msg: str) -> u64!LexError

Delimited: a delims char opens the token, which spans to just past the next occurrence of the same char. ok(0) when the first char isn't a delimiter. With a non-empty escapes set, a backslash escapes its next char: an allowed char is content (an escaped delimiter doesn't close), a disallowed one is a hard error, and a dangling backslash at the end of the source leaves the token unterminated. A token still open at the end of the source is a hard error (at is the token's absolute start, so error spans land in the real source).

unterminated_msg fn 

fn unterminated_msg(msg: str) -> str

The message for an unterminated scan: a rule's own unterminated override, or the generic default when it left the field empty.

between_len fn 

fn between_len(self: str, at: u64, open: str, close: str, msg: str) -> u64!LexError

Between: the open spelling opens the token, which runs to just past the next full occurrence of close. ok(0) when self doesn't start with open. The close scan starts past the open and matches the whole close spelling, so a partial close inside (a lone "/"" under a """ close) is content, not a terminator, and open/close may be multi-char and differ. No escapes — contents are verbatim. A token still open at the end of the source is a hard error (at places the span in the real source).

nested_len fn 

fn nested_len(self: str, at: u64, open: str, close: str, msg: str) -> u64!LexError

Nested: the depth-tracked Between. The open spelling opens the token at depth 1; each further open raises the depth and each close lowers it, so the token ends just past the close that returns the depth to 0. ok(0) when self doesn't start with open. open is tested before close so an overlap can't misclassify, but the two must be distinct for nesting to mean anything. No escapes — contents are verbatim. Still open (depth > 0) at the end of the source is a hard error (at places the span in the real source).

to_eol_len fn 

fn to_eol_len(self: str, marker: str) -> u64

ToEol: the marker, then everything up to (not including) the next newline. 0 when self doesn't start with the (non-empty) marker.

to_eol_unless_len fn 

fn to_eol_unless_len(self: str, marker: str, blocked: str) -> u64

ToEolUnless: to_eol_len, refused when the character right after the marker is one blocked claims. End of input or a newline right after the marker is *not* blocked — an empty comment line is a comment.

number_end fn 

fn number_end(self: str, int_end: u64) -> u64

The end of the number whose integer part ends at int_end: extends past a fraction (. then at least one digit), then past an exponent (e or E, an optional sign, then at least one digit). Either part may be absent; int_end comes back unchanged when neither matches.

float_len fn 

fn float_len(self: str) -> u64

Float: a digit run that extends past a fraction and/or exponent. A bare digit run is 0 (no match) — it belongs to the int rule.

int_len fn 

fn int_len(self: str) -> u64

Int: the length of an optional leading - then a digit run. 0 (no match) when there's no digit run — including a - *not* immediately followed by a digit (a - before a space or a letter is left for a - operator rule, so - 5/-x don't match). That decline is the entire sign-vs-operator disambiguation: with an Int rule before the - operator rule, -5 is a signed literal while - 5/-x are the operator; put the operator first and every - is the operator and Int is unsigned.

token_value fn 

fn token_value(m: Matcher, text: str) -> TokenValue

The value a token of matcher m carries, computed from its matched text (src[at..at+n], delimiters included) — see the value table on Matcher. Only the string-valued matchers carry a computed value; everything a rule can recover by slicing its span (Int/Float numeric runs, identifiers, …) is NoValue, so the rule's emit interprets the text itself. Template returns NoValue here only because its tokens are built inside template_scan, which attaches each segment's value itself.

apply_emit fn 

fn apply_emit<K: any>(e: Emit<K>, __spat$31078: SpanStr, value: TokenValue) -> K!LexError

Build a token's kind by applying the rule's emit to its content string — the matcher-computed value (a delimited string, stripped) when there is one, else the raw matched text. Bare ignores it; Of applies its constructor; Try does too but may fail with a message (paired with the token span to make a LexError). step_result fn 

fn step_result<K: any>(r: TokenRule<K>, src: str, at: u64, n: u64) -> StepResult<K>!LexError

A simple (single-token) matcher's outcome: a decline when the matched length n is 0, otherwise n chars consumed producing the rule's one token — recorded as trivia for a trivia rule, or nothing at all for a skip rule. The token's kind comes from the rule's emit applied to the matcher-computed value, which can fail on an emit/value-shape mismatch.

lex_step fn 

fn lex_step<K: any>(src: str, at: u64, rules: TokenRule<K>[]) -> StepResult<K>!LexError

One lexing step at absolute position at: tries each rule in order (first match wins) and returns the winning rule's outcome — see StepResult. Every arm but Template computes how far its matcher reaches (0 for no match — no matcher matches empty input, so a nonzero length always means progress) and wraps it via step_result; a Template's multi-token run doesn't fit a single length, so its arm builds the outcome directly. Mutually recursive with template_scan: an interpolation re-enters this full rule set, so template literals nest.

seg_emit fn 

fn seg_emit<K: any>(e: Emit<K>, text: str, seg: Seg, span: Span) -> K!LexError

Apply a Template rule's emit to one segment's raw text and its position. The emit must be an OfSeg (or its fallible sibling TrySeg) — a template produces several kinds per literal, one per segment position, which only a segment emit can distinguish; any other option is a lex error. A TrySeg that returns err(msg) carries the segment's span.

template_scan fn 

fn template_scan<K: any>(src: str, at: u64, delim: str, escapes: str, finalize: (str[]) -> str[], emit: Emit<K>, rules: TokenRule<K>[], unterminated: str) -> StepResult<K>!LexError

Template: scans a whole template literal at at (the caller verified the opening delim); the result's tokens are the literal's whole run and its end sits just past the closing delim. A text segment runs until the closing delim (matched in full, like Between) or a {, which ends the segment and opens an interpolation (see interp_scan).

**A segment's span runs brace to brace, and its value does not.** The span takes the delimiter or } that opens the segment and the delimiter or { that closes it; the value is what lies strictly between. Keeping the two starts apart is what makes the token stream *tile* the source — every byte of a template under exactly one token — which a concrete syntax tree needs and a token stream alone does not care about. They were once the same variable, and the } closing an interpolation was then the one byte of a template that belonged to no token at all. The text segments are collected first (with their spans and the interpolation token runs between them), then handed to finalize_template — which post-processes them as a group and emits each. A nested template inside an interpolation is fully lexed (and its own segments finalized) by the recursive interp_scan, so each template_scan only ever handles its own direct segments. escapes still governs *scanning* as in delimited_len, including the hard error on an unknown escape and the dangling backslash falling through to run the literal out unterminated.

finalize_template fn 

fn finalize_template<K: any>(src: str, finalize: (str[]) -> str[], emit: Emit<K>, seg_texts: str[], seg_spans: Span[], interp_runs: StepResult<K>[], end: u64) -> StepResult<K>!LexError

Emit a template literal's tokens: apply the caller's finalize to all of its text segments as a group (it returns one finalized text per segment), then emit each finalized segment — its position Plain for a lone segment, else Head/Middle/Tail — via the rule's OfSeg/TrySeg emit, interleaved with the interpolation token runs (interp_runs[k] following segment k). end sits just past the closing delim.

interp_scan fn 

fn interp_scan<K: any>(src: str, at: u64, open: u64, rules: TokenRule<K>[]) -> StepResult<K>!LexError

A template interpolation's { ... } body: lexes expression tokens with the full rule set from at (just past the opening {, which sits at open) until the } balancing it; that closing } is consumed without a token of its own — it's the template's delimiter, not an expression token, and it is the *next* text segment's span that covers it (see template_scan). Depth moves by what each step consumed: a step consuming exactly { or } (a brace lexed as its own token — set/dict literals, blocks) raises/lowers it, while a brace buried inside a bigger token (a delimited string's content, a nested template) doesn't. The result's end sits just past the closing }.
