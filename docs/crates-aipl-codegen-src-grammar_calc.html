CalcTok variant pub 

variant CalcTok

Two token kinds: digit runs, and every one-character operator or bracket. The grammar tells the operators apart by Literal, so their kind never has to. (Imported unaliased, against the usual Literal as Lit: this grammar's own AST already calls a case Lit, and an import colliding with a local is a hard error. The alias is a convention, not a requirement.)

  • Punct

calc_rules fn 

fn calc_rules() -> TokenRule<CalcTok>[]

Whitespace is trivia rather than skipped, so the concrete tree covers every byte and reconstructs the source exactly.

The punctuation rule sits *ahead* of Int, which makes every - its own token and Int unsigned. That is the ordering this grammar needs: negation is a rule (unary), so a - the lexer had swallowed into the literal would be invisible to it — 1 -2 would lex as two numbers and parse as nothing.

lower_atom fn 

fn lower_atom(src: str, node: Cst, kids: Calc[]) -> Calc!ParseError

A parenthesized expression lowered one interior child, and a literal lowered none — so the absence of a child is what says "this is a number", and its text is the node's own.

The one build here that can fail: a literal too big for an i64. It is a lowering error, not a parse error, and parse hands it back unchanged.

calc_grammar fn pub 

pub fn calc_grammar() -> Grammar<CalcTok, Calc>

The calculator grammar: + - * / % ^ over integer literals, with ^ right-associative and unary - binding tighter than any of them.

Only atom is labelled, so a failure deep in an expression reports as "an expression" rather than as the three productions it is made of.

render_calc fn pub 

pub fn render_calc(self: Calc) -> str

self printed back as source, fully parenthesized — every application gets brackets, so the text shows the tree and needs no precedence rules to read.

Round-trips with parse_calc: parse_calc(render_calc(v)) == v.

eval_calc fn pub 

pub fn eval_calc(self: Calc) -> i64

self evaluated as integer arithmetic. Division is saturating and ^ is integer exponentiation with a negative exponent yielding 0, so evaluation is total — a calculator's arithmetic policy is its own, not the parser's.
