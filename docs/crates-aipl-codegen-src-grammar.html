ParseError struct 

struct ParseError

Why a parse failed: a message, and the span of the offending source (absolute into the parsed string — slice it to show the offender, or hand it to caret_block.aipl for the rustc-style underline). Mirrors lexer.aipl's LexError, and for the same reason: the two halves of a front end should report failure in one shape.

A *grammar* error — an unresolved rule reference, a rule that can loop forever — has no source to point at and carries the empty 0..0.

failure_message fn 

pub fn failure_message(self: str!ParseError) -> str

What a failed parse said — or, when it unexpectedly *succeeded*, a note carrying what it produced, so a broken assertion says which way it broke.

For .test blocks, which is where the distinction matters: an assertion on a message that silently parses instead reads as a mismatched string with no clue why. Pairs with map_ok, which is what turns a parse of any AST type into the str!ParseError this takes: parse_x(src).map_ok(render_x).failure_message().

Prec struct 

struct Prec

One precedence level of a Climb: the operators that share it, how tightly they bind (power, higher wins), and whether they associate to the right. Levels are matched in order, so a spelling belongs to exactly one.

Rule variant 

variant Rule<K: variant>

One rule shape, as plain data. Ordered choice makes this a PEG, not a CFG: OneOf commits to the first alternative that matches, so alternatives are tried in the order written and there is no ambiguity to resolve.

  • Term(Case<K>)

    Any one token whose kind is the case k — Term(Name) matches every identifier, whatever text it carries. The one place a rule looks at a token's *kind* rather than its text. k is a Case<K>, which is a case with no payload: naming a kind takes no value of that kind, so there is no dummy to invent and none to accidentally read.

  • Literal(str)

    One token whose source text is exactly s. Punctuation and keywords, matched by what they are written as rather than by the kind that lexed them — the counterpart of Term, which asks the kind and ignores the text. Grammar files conventionally import it aliased (Literal as Lit): it is by far the most-written rule in any real grammar, and the short form is what keeps a production on one line. A convention, not a requirement — grammar_calc.aipl imports it unaliased, its own AST having a Lit case already, and an import colliding with a local is a hard error.

  • Then(Rule<K>[])

    Every rule in order; the matched children concatenate.

  • OneOf(Rule<K>[])

    The first alternative that matches, in order.

  • Many(Rule<K>, min: u64 = 0, max?: u64 = none, sep?: Rule<K> = none, trailing_sep: bool = true, leading_sep: bool = false, nested_in?: (Rule<K>, Rule<K>) = none, spaced: bool = false, sorted: bool = false, style?: ListStyle = none, group?: u64 = none)

    The rule repeated until it stops matching — by default a PEG *; Many(r, min=1) is a +, and Many(r, min=1, max=1) is exactly one. A rule that can match empty input would spin here forever, so the driver refuses one outright rather than hanging.

    Between sep, trailing_sep and leading_sep, one rule covers every list a grammar writes. An LR grammar spells each combination as its own wrapper production around a left-recursive pair — x_list | x_list COMMA | _ — and which of the four you picked is the thing that is easy to get subtly wrong; here it is arguments with names.

    sep and max are both written with the ? on the *name*: a caller gives the rule itself (sep=Lit(",")), and leaving it out is what yields none. A caller that already holds an optional — link_rule and desugar_rule, rebuilding a rule they took apart — forwards it with sep?=...

    • Rule<K>

      The rule repeated.

    • min: u64 = 0

      The fewest repetitions that count as a match.

    • max?: u64 = none

      The most repetitions taken. A bound stops the repetition rather than failing it: the items past max are simply not this rule's, and the enclosing rule sees them. That is what makes min=1, max=1 mean "one item, in brackets" when it carries a nested_in — a group that holds one thing rather than a list.

    • sep?: Rule<K> = none

      Given, this is a *separated* list: the rule, then sep and the rule again for as long as the separator keeps appearing.

    • trailing_sep: bool = true

      What happens to a separator with nothing after it — consumed ([1, 2,] is the list) or rewound and left for the enclosing rule to complain about. It still applies at the max bound: a separator after the last item ends the list rather than starting the item that would have been next, so Many(x, sep=comma, max=2) takes 1, 2, whole — the same answer it gives when the items run out instead.

    • leading_sep: bool = false

      trailing_sep's mirror at the front: the list may open with a separator before its first item (| A | B as well as A | B), which is the shape a variant's cases take once they break one per line.

    • nested_in?: (Rule<K>, Rule<K>) = none

      The bracketed-list shorthand: given (open, close) it is a bracket pair around this Many, which is what makes it a *group* before anything else runs. Nearly every bracket pair in a real grammar holds a list, and writing the brackets as an argument of the list beats wrapping the list in a separate rule — Many(param, sep=comma, nested_in=parens()) against a separate production wrapping the list in brackets.

      A pair, so "exactly two brackets" is the type rather than a length desugar has to check and a caller has to get right. It was an array until generic tuples worked — a tuple whose elements mention a type variable has no layout until monomorphization binds it, which is now what lt_ty defers to instantiate_generic.

    • spaced: bool = false

      Whether the brackets take inner spaces while the list stays flat — { a, b } against (a, b). The rest of the list's *style* is read off the Many rather than restated: sep from this rule's own separator and trailing from trailing_sep, which is the same fact said once instead of twice (strict JSON's [1, 2,] is an error *and* is never printed). Only this one cannot be derived, so it is here.

    • sorted: bool = false

      Whether a formatter orders the items rather than keeping them as the author wrote them — by each item's leading token, in ordinary str order. A list that sorts is a keyed list, and the key leads: a JSON member's "name", an import's wrapping_add in wrapping_add as +. The parser never reads it; like spaced it is here because the grammar is where a list's style is stated, and the printer reads it back off the group.

    • style?: ListStyle = none

      The group's layout stated outright instead of derived, which is what lets a bracket pair hold something whose list lives one production down: (args) is a group that wraps like a comma list, but the Many holding it has no separator of its own to read one off — args does. Given, it replaces the derivation entirely, spaced included.

      The freedom is real and so is the hazard: nothing checks a stated sep against the one the rule actually matches, so a style that disagrees makes the printer write a separator the parser will not accept. Derive where you can, state it where the list is not this rule's.

      The shape that needs stating is a group holding a list that lives one production down, and inlining the list into the group removes it — at which point this argument, and the disagreement it admits, both go away. Which of those wrapper productions can fold is what the lowering decides; PARSER_LIBRARY.md's 5d carries the plan.

    • group?: u64 = none

      The index of this bracket pair's style in the grammar's groups, stamped by link (see Grammar). No grammar file writes it, and a Many without a nested_in never carries one.

  • Maybe(Rule<K>)

    The rule, or nothing. Always matches.

  • Named(str)

    A reference to the production called n. link rewrites every one of these to a NamedIdx, so the driver never compares strings.

  • NamedIdx(u64)

    A reference to production i, and the *only* rule that builds a CST node — one Tree(i, ..) per reference matched.

  • Climb(Rule<K>, Prec[])

    Precedence climbing — an atom, then binary operators drawn from precs, nested by binding power. Each application nests under the *enclosing* production's index, so 1 + 2 * 3 yields a node per operand rather than one flat run.

  • Refuse(Refusal)

    A rule that never matches: reached, it fails the whole parse with the message its Refusal gives. Refusal is not a miss — no enclosing choice, option or repetition backtracks out of it — so it is only ever reached on purpose, after a sequence has matched the thing worth refusing: Then([Named("operator"), Refuse(..)]) accepts an operator and then rejects it, and the error underlines what the sequence matched.

    This is how a grammar names a shape the language *used to* have, or that a reader would plausibly write, and says something more useful than the "expected X, found Y" a plain non-match would produce.

    The one rule that can hold a function value, which costs Rule its == — a rule is compared through show_rule instead.

Refusal variant 

variant Refusal

What a Refuse says: a fixed message, or one computed from what was matched in front of it — the tokens the enclosing sequence accepted before reaching the refusal, run together with single spaces. Fn is what lets the message name the offender: refusing import { + }, it is handed + and can say which aliases to write instead. A refusal reached with nothing in front of it is handed "".

Fn is a function value, so a Refusal — and any Rule holding one — has no ==; see Build for the same constraint on lowerings.

Build variant 

variant Build<A: any>

How a production's matched node becomes a value of the caller's AST type A.

Three shapes, by what the lowering reads — the whole node, its children, or its text — each in a total form and a Try form that can refuse with a ParseError the driver passes straight through (a literal that overflows, a duplicate key). A lowering is declared with exactly what it uses and the failure it can have: a total one returns its A bare, so no ok(..) wraps a value that could not be anything else.

Every arm carries an A (a function returning one, or the value itself), so each pins the type parameter on its own; a payload-free arm could not, which is why there is no NoLower.

Function values are non-capturing and non-generic (check.rs), so a lowering is a named top-level fn lower_x(..), a constructor (Kids(Object)), or a lambda that reads only its parameters — whose types it takes from the arm's payload, so Text(|t| Bool(t == "true")) needs no annotation. They also can't be compared with ==, which is why the tests below assert on what a grammar *parses*, never on a grammar value — the same constraint lexer.aipl lives with.

  • Mk((str, Cst, A[]) -> A)

    The general form: the source text, the node itself, and the already- lowered values of its interior children (nodes, in match order).

  • TryMk((str, Cst, A[]) -> A!ParseError)

    Mk for a lowering that can refuse what it matched.

  • Kids((A[]) -> A)

    Only the children — a node that is its children regrouped (Object(kids)).

  • TryKids((A[]) -> A!ParseError)

    Kids for a lowering that can refuse.

  • Text((str) -> A)

    Only the node's token text (token_text, the matched tokens run together) — a leaf-only node whose value is its spelling.

  • TryText((str) -> A!ParseError)

    Text for a lowering that can refuse — a number that overflows.

  • Const(A)

    Nothing at all: the value itself — a keyword production.

ListStyle struct 

struct ListStyle

How a bracketed list lays out: what separates its items, whether the brackets take inner spaces while the list stays on one line ({ a, b } against (a, b)), and whether a separator is written after the last item once it breaks.

The brackets themselves are not here: they are the open and close rules of the repetition this style belongs to, matched from the source like anything else. A style is only the handful of decisions the brackets cannot answer. An empty sep is the juxtaposed list, where items are separated by nothing but the space between them: (a b c), and every S-expression ever written. A group holding one thing rather than a list — (expr) — is the same shape with no separator ever reached.

sorted is the one decision that is not about where the items go but which order they go in: the printer orders them by their leading token rather than keeping the author's order. A JSON object's members, an import's names.

wraps: false is the group that is a bracket pair and nothing more. A block { .. } is one: it is a pair the parser should know about, so an unclosed brace is reported against the brace that opened it, but its contents are statements rather than a list and breaking them at a width is not what a formatter does with them. Such a group lays out Inline, like any other run of children.

In the nested_in shorthand it is not written by hand: a Many bounded at one item is not a list, so desugar reads wraps: false off max=1.

Layout variant 

variant Layout

How a production's matched children are joined into a Doc — the formatting half of a language description, read by format.aipl exactly as Rule is read by parse.aipl.

The vocabulary is deliberately small, and it is not the whole of a formatter: comment attachment, call hugging and chain breaking are judgement about *this* language and do not fall out of any grammar. What these two do cover is the mechanical majority — the productions whose layout is fully determined by the tokens they matched.

Wrapping is not here, and that is the point of nested_in. Where a list breaks is a property of the bracket pair holding it, not of the production the pair happens to sit in, so it is written at the brackets and read back off the Group node they build. A production may hold several groups, each with its own style — match (e) { .. } is two — which is exactly what a single field on the production could not say.

Production struct 

struct Production<K: variant, A: any>

One named production: its rule, and what each downstream pass needs from it.

name is both the reference target (Named("expr")) and the CST node's name. expect_as is the label an error blames when this production fails having matched nothing — the reified form of the LR parser's SYMBOL_DISPLAY_NAMES, which collapses expr/term/unary/atom to one word. Empty means *transparent*: a plumbing production never surfaces in a message, and the finer expectations from inside it are what the reader sees. scope is the highlighter hint; it is carried, not yet consumed. layout is how the formatter joins what this production matched.

layout has no default, unlike the two hints above it, and that is the compiler's decision rather than the design's: a struct field's default must be a literal, and Layout has no literal form. A bare = Inline is refused ("unknown identifier"), Layout? is refused as a field type because Layout is not recursive and so is not boxed, and a = inline() call *is* accepted but is then resolved in every file that constructs a Production — so a grammar that never mentions layout would have to import a function it never names, and the error when it forgets points at an unrelated line. Spelling the layout out is the honest version of that, and a grammar saying how each production prints beside how it parses is the whole point of the field.

Grammar struct 

struct Grammar<K: variant, A: any>

A whole language: its productions, in order. Position is identity — a NamedIdx and a Tree both name a production by its index here — so the order of this array is part of a linked grammar's meaning.

groups is the same idea for bracket pairs: link collects every bracketed ListStyle into it, in the order the rules mention them, and stamps the rule with the entry's index. A Group node then carries that index rather than a style, which keeps the CST as free of layout as it is of production names. It is empty on an unlinked grammar and written only by link, so no grammar file ever spells it out.

show_rule fn 

pub fn show_rule<K: variant>(r: Rule<K>) -> str

r written back out as the constructor calls that build it — the debug view of a rule, and how a test asserts on one. A Rule cannot be compared with == (a Refuse may hold a function value) or rendered with to_str, so this is the one way to look at one. Defaulted arguments of a Many are written only where they differ from the default, so what is shown is what a grammar author would have written.

desugar_rule fn 

pub fn desugar_rule<K: variant>(r: Rule<K>) -> Rule<K>!ParseError

r with every bracketed repetition's style settled: stated, or read off the rule it belongs to.

Run before anything else looks at a rule, so the style a group carries is already the one it means by the time the driver, the formatter, the EBNF dump or the FIRST sets see it. The rule shape is unchanged — a bracketed Many is the storage form as well as the written one — so this only ever fills the slot a caller left empty.

The style is derived here — sep from the list's own separator, trailing from trailing_sep, spaced as given — so a grammar states each of those once. wraps comes from max: a Many in brackets is a list by construction and lists wrap, *unless* it is bounded at one item, which makes it a bracket pair holding one thing ((expr), a block's braces) rather than a list. There is nothing to break at a width in that case, so it lays out inline.

link fn 

pub fn link<K: variant, A: any>(g: Grammar<K, A>) -> Grammar<K, A>!ParseError

g with every rule reference resolved: each Named(name) rewritten to the NamedIdx(index) of the production it names, so the driver resolves a reference by indexing rather than by comparing strings. Fails when a reference names no production, or when two productions share a name.

Idempotent — a NamedIdx passes through — so a grammar may be linked once and reused, or handed to parse unlinked and linked per call.

group_styles fn 

fn group_styles<K: variant>(r: Rule<K>) -> ListStyle[]

Every group style in r, in the order the rules mention them: a group's own style first, then the styles inside its brackets. That order is the contract with link_rule, which hands out indices by walking the same tree the same way — get the two out of step and a Group names another group's style.

Both spellings answer, so an already-linked rule reports the same list as the rule it was linked from, which is what makes link idempotent.
