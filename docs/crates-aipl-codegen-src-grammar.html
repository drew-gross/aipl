ParseError struct 

struct ParseError

Why a parse failed: a message, and the span of the offending source (absolute into the parsed string — slice it to show the offender, or hand it to caret_block.aipl for the rustc-style underline). Mirrors lexer.aipl's LexError, and for the same reason: the two halves of a front end should report failure in one shape.

A *grammar* error — an unresolved rule reference, a rule that can loop forever — has no source to point at and carries the empty 0..0.

failure_message fn 

pub fn failure_message(self: str!ParseError) -> str

What a failed parse said — or, when it unexpectedly *succeeded*, a note carrying what it produced, so a broken assertion says which way it broke.

For .test blocks, which is where the distinction matters: an assertion on a message that silently parses instead reads as a mismatched string with no clue why. Pairs with map_ok, which is what turns a parse of any AST type into the str!ParseError this takes: parse_x(src).map_ok(render_x).failure_message().

Build variant 

variant Build<A: any>

How a production's matched node becomes a value of the caller's AST type A: a function from the source text, the node itself, and the already-lowered values of its interior children (nodes, in match order). It may fail — a literal that overflows, a duplicate key — with a ParseError the driver passes straight through.

A one-arm variant rather than a bare function type, so a later arm can be added without every grammar changing shape. It stays one arm deliberately: a payload-free NoLower would pin no A of its own, leaving nothing to infer the type parameter from, so a production with nothing to lower passes a trivial named function instead.

Function values are non-capturing and non-generic (check.rs), so each is a named top-level fn lower_x(src: str, node: Cst, kids: A[]) -> A!ParseError. They also can't be compared with ==, which is why the tests below assert on what a grammar *parses*, never on a grammar value — the same constraint lexer.aipl lives with.

  • Mk((str, Cst, A[]) -> A!ParseError)

ListStyle struct 

struct ListStyle

How a bracketed list lays out: what separates its items, whether the brackets take inner spaces while the list stays on one line ({ a, b } against (a, b)), and whether a separator is written after the last item once it breaks.

The brackets themselves are not here: they are the open and close rules of the NestedIn this style belongs to, matched from the source like anything else. A style is only the handful of decisions the brackets cannot answer. An empty sep is the juxtaposed list, where items are separated by nothing but the space between them: (a b c), and every S-expression ever written. A group holding one thing rather than a list — (expr) — is the same shape with no separator ever reached. wraps: false is the group that is a bracket pair and nothing more. A block { .. } is one: it is a pair the parser should know about, so an unclosed brace is reported against the brace that opened it, but its contents are statements rather than a list and breaking them at a width is not what a formatter does with them. Such a group lays out Inline, like any other run of children.

In the nested_in shorthand it is not written by hand: a Many bounded at one item is not a list, so desugar reads wraps: false off max=1.

Layout variant 

variant Layout

How a production's matched children are joined into a Doc — the formatting half of a language description, read by format.aipl exactly as Rule is read by parse.aipl.

The vocabulary is deliberately small, and it is not the whole of a formatter: comment attachment, call hugging and chain breaking are judgement about *this* language and do not fall out of any grammar. What these two do cover is the mechanical majority — the productions whose layout is fully determined by the tokens they matched.

Wrapping is not here, and that is the point of NestedIn. Where a list breaks is a property of the bracket pair holding it, not of the production the pair happens to sit in, so it is written at the brackets and read back off the CGroup node they build. A production may hold several groups, each with its own style — match (e) { .. } is two — which is exactly what a single field on the production could not say.

  • Inline

Production struct 

struct Production<K: variant, A: any>

One named production: its rule, and what each downstream pass needs from it.

name is both the reference target (Named("expr")) and the CST node's name. expect_as is the label an error blames when this production fails having matched nothing — the reified form of the LR parser's SYMBOL_DISPLAY_NAMES, which collapses expr/term/unary/atom to one word. Empty means *transparent*: a plumbing production never surfaces in a message, and the finer expectations from inside it are what the reader sees. scope is the highlighter hint; it is carried, not yet consumed. layout is how the formatter joins what this production matched.

layout has no default, unlike the two hints above it, and that is the compiler's decision rather than the design's: a struct field's default must be a literal, and Layout has no literal form. A bare = Inline is refused ("unknown identifier"), Layout? is refused as a field type because Layout is not recursive and so is not boxed, and a = inline() call *is* accepted but is then resolved in every file that constructs a Production — so a grammar that never mentions layout would have to import a function it never names, and the error when it forgets points at an unrelated line. Spelling the layout out is the honest version of that, and a grammar saying how each production prints beside how it parses is the whole point of the field.

Grammar struct 

struct Grammar<K: variant, A: any>

A whole language: its productions, in order. Position is identity — a NamedIdx and a CTree both name a production by its index here — so the order of this array is part of a linked grammar's meaning.

groups is the same idea for bracket pairs: link collects every NestedIn's ListStyle into it, in the order the rules mention them, and rewrites the rule to a NestedIdx naming the entry. A CGroup node then carries an index rather than a style, which keeps the CST as free of layout as it is of production names. It is empty on an unlinked grammar and written only by link, so no grammar file ever spells it out.

desugar_rule fn 

pub fn desugar_rule<K: variant>(r: Rule<K>) -> Rule<K>!ParseError

r with every bracketed-list shorthand written out: a Many carrying nested_in=(open, close) becomes the NestedIn it is shorthand for, wrapping the same Many with the brackets removed.

Run before anything else looks at a rule, so only one spelling ever reaches the driver, the formatter, the EBNF dump or the FIRST sets. That is the whole point of making it sugar rather than a second rule shape: the passes downstream stay unaware it exists.

The style is derived here — sep from the list's own separator, trailing from trailing_sep, spaced as given — so a grammar states each of those once. wraps comes from max: a Many in brackets is a list by construction and lists wrap, *unless* it is bounded at one item, which makes it a bracket pair holding one thing ((expr), a block's braces) rather than a list. There is nothing to break at a width in that case, so it lays out inline.

link fn 

pub fn link<K: variant, A: any>(g: Grammar<K, A>) -> Grammar<K, A>!ParseError

g with every rule reference resolved: each Named(name) rewritten to the NamedIdx(index) of the production it names, so the driver resolves a reference by indexing rather than by comparing strings. Fails when a reference names no production, or when two productions share a name.

Idempotent — a NamedIdx passes through — so a grammar may be linked once and reused, or handed to parse unlinked and linked per call.

group_styles fn 

fn group_styles<K: variant>(r: Rule<K>) -> ListStyle[]

Every group style in r, in the order the rules mention them: a group's own style first, then the styles inside its brackets. That order is the contract with link_rule, which hands out indices by walking the same tree the same way — get the two out of step and a CGroup names another group's style.

Both spellings answer, so an already-linked rule reports the same list as the rule it was linked from, which is what makes link idempotent.

link_rule fn 

fn link_rule<K: variant>(r: Rule<K>, names: str[], base: u64) -> Rule<K>!ParseError

One rule with every Named(n) in it rewritten to NamedIdx(i) and every NestedIn to a NestedIdx naming its entry in the grammar's groups table. Fails when a reference names no production — the error a grammar author most wants caught before a parse rather than during one.

base is the index the first group in r takes; the rest follow in group_styles order. It is threaded by arithmetic rather than by a running counter because a rule is a tree and try_map has nowhere to keep one.
