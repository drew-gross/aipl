The match_value_or_err lint:

match (o) { some(v) => ok(v), none => err(e) }

— an optional turned into a result by naming both cases. That is exactly o.value_or_err(e).

The none arm building an err is what identifies the shape: it is the bridge from the optional world to the result world, and value_or_err is the name of that bridge. Arm order does not matter.

The some arm is not constrained to the identity ok(v), because the rewrite does not need it to be. some(v) => ok(f(v)) is ok(f(o.value_or_err(e)?)) — the same value_or_err, with ? doing the early return the none arm was doing by hand. The advice says which of the two it is, since the second reads quite differently from the first.

The none arm may also leave with the error — a block holding nothing but return err(e); — which is the statement form of the same bridge: the match runs for effect, the some arm's block is the rest of the function, and the return stands in for the ?. That one rewrites to let v = o.value_or_err(e)?; followed by the some arm's body, with v the arm's binder, and the advice spells it that way.

A computed error is fine, and that is the point of is_sinkable. Written out, value_or_err's error is an ordinary call argument and so looks eager — but the optimizer inlines the builtin and sinks the argument into the none branch, so it is built exactly when the match built it. Measured on a struct error interpolating a runtime string: both spellings allocate the same, to the byte. This is where the rule differs from match_value_or, whose is_constant_default guard predates that reasoning.

The hit points at the none => err(..) arm's body, not the whole match: #[allow] is line-scoped, so a hit spanning the multi-line match could never be squelched. This arm is the one that identifies the shape — the some arm varies — and its err call always starts on the arm's own line. For the block form that line is the return's: a marker after the arm's { would not survive formatting.
