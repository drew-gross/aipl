UnfilledHit struct 

struct UnfilledHit

A hit whose message names builtins the way the file that was linted spells them. A lint cannot say how: it reads one function, and the spelling is in the import list, so it reports the message in parts — each stretch of text followed by the name of a builtin, then a closing stretch — and the caller fills the names in. A file that does not import a builtin is told to, which the lint need not know either.

spans_its_text fn 

pub fn spans_its_text(self: Expr) -> bool

Whether self's span covers exactly the text that spells it, so the source can be spliced back into advice. Only a name and a field path off one qualify: their spans run from the first character to the last. Most other forms do not — a call's span stops before its closing paren, so f(x) splices back as f(x, which doesn't parse — and the ones that might are left out rather than each having to be re-checked whenever a span moves.

on_functions fn 

pub fn on_functions(self: Program, lint: (Function) -> LintHit[]) -> LintHit[]

Lints come in two kinds. A program lint is a function of the whole Program (unused_imports, which compares the imports with every name the file mentions). A function lint is a function of one Function, and [on_functions] is what runs it over a program, so no function lint decides for itself which bodies to look at.

Every body that is code to check is a function here: each function, the .test block it carries, the .performance block it carries, and the helpers declared in a .test block. A block is checked as a function of its own when tests run, so it is handed over as one — no parameters, no return type, the block as its body.
