The names the parser gives functions it synthesizes from a declaration's attributes, and the inverse: what a function's name says it is.

A .test({ .. }) block on f becomes the function __test$f; a function declared inside that block is hoisted to __test$f$helper; a .benchmark({ .. }) block on f becomes __benchmark$f, whose own .test body is the block. A $ cannot appear in a source name, so no program can spell any of them, and a $ past the prefix is the mark of something synthesized from a body rather than the body itself — a lambda lifted out of a test body is __test$f$lambda0, and its ? acts on the lambda's own return type.

Rust asks the questions of this file through the FFI (fn_role, test_fn_name, benchmark_fn_name); test_helper_name is only asked by the pass that hoists helpers, which is AIPL too.

FnRole variant 

variant FnRole

What a function's name says it is. A source name is Plain.

  • TestBody: exactly a .test body (__test$f, or __test$__benchmark$f

for a .benchmark block).

  • TestHelper(helper): a function hoisted out of a .test block, with the

name it was declared with.

  • Benchmark(source): the function standing for source's .benchmark

block.

  • Plain

  • TestHelper(helper: str)
  • Benchmark(source: str)

unattached_test_name fn 

pub fn unattached_test_name(ordinal: u64) -> str

The name of the function standing for a top-level test({ .. }) block, which is attached to no function. ordinal counts the file's such blocks from 1, so the name does not move when anything else in the file does (a pinned aipl report lists it). The name is a plain function's, and its own .test body is the block, so the block reaches everything downstream as the test code of a function nobody calls.
