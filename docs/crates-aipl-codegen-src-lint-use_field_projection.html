The use_field_projection lint: a lambda in a map that does nothing but take its parameter through member reads and method calls is the $ projection.

A lambda whose whole body is its parameter taken through a chain of member reads and method calls — |x| x.name, |x| x.0, |x| x.f(args), |x| x.a.f(b).c, |x| to_str(x) — is xs$name, xs$0, xs$f(args), xs$a$f(b)$c and xs$to_str(): each step written once, with no name for the element to introduce and then repeat. And a bare function name, xs.map(f), is xs$f().

Only the shape $ stands for qualifies. The parameter has to be the root of the chain and appear nowhere else (|x| x.f(x) needs the name), it has to be unannotated, since $ has no place to write a type, and every call in the chain has to be one $ can make — a function of this file whose first parameter is named self, which is what method-call syntax is defined by, a builtin, or a call already written as a method. A function from another file is not known here — its parameters are not in view when a file is linted — so it is never advised. An operator is never a step: |x| x + 1 does something with x.

The hit points at the lambda, or at the bare name — a short span that begins on the line the #[allow] would be written on. The lint runs before checking, so it cannot tell a sequence from an optional; $ maps either, as map does.
