Far struct 

struct Far

The furthest failure seen so far: the token position nothing could be matched at, and the deduped labels of everything that *was* expected there.

This is the reified form of what an LR table gives you for free — the state's expected-symbol set — and it is why Production.expect_as exists: under ordered choice a more specific alternative can fail deeper than the one that was really meant, so a label collapsing a family of rules to one word ("an expression") is what keeps the message readable.

Step struct 

struct Step

One rule's result at one position: whether it matched, where it left off, the CST children it contributed to its parent, and the furthest failure so far.

hit: false is an ordinary non-match — the caller backtracks and tries something else — and is *not* an error. A ParseError is reserved for what no alternative could fix: a malformed grammar, or a build that refused.

Parser struct 

struct Parser<K: variant, A: any>

What the driver parses against: the tokens, the trivia the lexer set aside, the linked productions, and end — one byte past the source's last byte.

The source itself is *not* here. Every token carries its own text (a SpanStr, see lexer.aipl), so matching a rule spelling reads the token and nothing else. end is all that remains of the source: the empty span at end of input, which error_at reports when a rule ran off the token list and there is no token to point at.

parse_cst fn 

pub fn parse_cst<K: variant, A: any>(src: str, lexed: LexResult<K>, g: Grammar<K, A>, start: str) -> Cst!ParseError

Parses src — already lexed into lexed — against grammar g, beginning at the production named start, and returns the lossless concrete syntax tree.

g is linked here, so it may be handed over unlinked; linking is idempotent, so a caller parsing repeatedly can link once and pay nothing again. Every token must be consumed: input left over after the start rule succeeds is an error, not a partial parse.

Fails with a ParseError carrying the span of the offending token — the *furthest* position anything was expected at, not the last one tried — or the empty span at the end of the source when the input simply ran out.

Prepared struct 

struct Prepared<K: variant, A: any>

A grammar linked, and optionally analysed, ready to parse with.

Everything here is a function of the grammar *alone* — the linked rules, the FIRST sets, the expectation labels — so a caller parsing more than one source builds this once with prepare and hands it to parse_prepared for each.

firsts and labels are empty when the grammar was linked but not analysed, which is what parse_cst does. The driver reads that as "nothing to prune on" and matches every production it reaches; the parse is identical, only slower. Analysis is a cost worth paying exactly once per grammar and never once per source.

prepare fn

g linked and analysed — build it once, parse with it many times. Fails the way link does: an unresolved reference, or a duplicate rule name.

lower fn 

pub fn lower<K: variant, A: any>(src: str, node: Cst, g: Grammar<K, A>) -> A!ParseError

Lowers a parsed tree to the caller's AST by calling each node's production build, depth first: a node's children are lowered before it, and only its *interior* children are passed (nodes) — a leaf has no lowered value, and its text is reachable from the node's own span.

Fails with whatever a build refused with, unchanged.

parse fn 

pub fn parse<K: variant, A: any>(src: str, lexed: LexResult<K>, g: Grammar<K, A>, start: str) -> A!ParseError

parse_cst followed by lower: the source's AST, with the concrete tree built and discarded in between. Use parse_cst when the tree itself is the point (a formatter, a highlighter), and this when only the AST is.

far_miss fn 

fn far_miss(far: Far, pos: u64, label: str) -> Far

far updated with "label was expected at pos". Deeper wins outright; equally deep joins the expected set (deduped); shallower is discarded. An empty label is a *transparent* production and records nothing.

far_unclosed fn 

fn far_unclosed(far: Far, open: Span[]) -> Far

far with the opening bracket that went unclosed at its position. Set by a bracketed repetition whose open matched and whose close did not, which is time anything knows a bracket was left hanging.

It rides on the furthest failure rather than aborting the parse, because under ordered choice a group failing to close is an ordinary non-match: (a) is parsed by trying the tuple (a, b) first and letting it fail at the comma. So this only reaches the reader when *no* alternative worked, which is exactly when a hanging bracket is the likely cause.

match_nested sets it only when the close was wanted past the last token — see there for why a closer failure is not evidence of anything. The first bracket to be blamed at a position keeps it. Groups fail from the inside out, so the first to record is the innermost one — and closing that is the edit the reader has to make first, even when an outer bracket is hanging too.

leaf_at fn 

fn leaf_at<K: variant, A: any>(p: Parser<K, A>, i: u64) -> Cst[]

The CST children consuming token i contributes: every trivia record between the previous token and this one, then the token's own leaf. Attaching trivia *before* its following token is what makes the leaf spans tile the source with no gaps, which is the whole losslessness property.

Looked up, not computed: a PEG asks this once per token *per attempt*, and it attempts a token many times. Filtering the whole trivia list on each ask was quadratic in the file — the largest compiler sources took a minute to parse, and this one call was most of it. attach_trivia does the same pairing once, by one merge over the two sorted lists.

attach_trivia fn 

fn attach_trivia<K: variant>(toks: Token<K>[], trivia: Token<K>[]) -> (Cst[][], Cst[])

Every token's leaf_at children, in token order, and the trivia left after the last token. Both lists arrive sorted by position and never overlap, so one pass that advances through the trivia as it walks the tokens pairs them off exactly as the per-token filter did — each trivia record lands in front of the first token that starts after it.

match_many fn 

fn match_many<K: variant, A: any>(p: Parser<K, A>, sub: Rule<K>, min: u64, max: u64?, sep: Rule<K>?, trailing_sep: bool, leading_sep: bool, nested_in: (Rule<K>, Rule<K>)?, group: u64?, pos: u64, cur: u64, far: Far) -> Step!ParseError

sub until it stops matching, at least min times — and, with a sep, with that separator between consecutive items.

A rule that can match empty input would repeat forever here, and AIPL has no break to escape with — so a zero-width iteration is refused outright, the same invariant lexer.aipl keeps by having no matcher accept empty input. It is a grammar bug, reported as one rather than hung on.

The separated case is the same loop with one step in front of each item after the first. What the separator matched is held back until an item follows it, because a separator with nothing after it is only part of the list when trailing_sep says so; otherwise the position rewinds to before it and the enclosing rule is the one that complains — which is how [1, 2,] can be either the list or a list followed by a stray comma.

match_group fn 

fn match_group<K: variant, A: any>(p: Parser<K, A>, gi: u64, brackets: (Rule<K>, Rule<K>), sub: Rule<K>, min: u64, max: u64?, sep: Rule<K>?, trailing_sep: bool, leading_sep: bool, pos: u64, cur: u64, far: Far) -> Step!ParseError

A bracketed repetition: open, then the items, then close, kept as one Group naming style gi. It parses exactly as Then of the three would; what it adds is on either side of that.

On the way in, the three runs stay separate in the tree, so the formatter knows which tokens are brackets without inferring it from where they sit. On the way out, a close that fails after open matched records the opening bracket's span on the furthest failure — the parse still backtracks like any non-match, but if nothing else works the message can say which bracket was left open.

match_prod fn 

fn match_prod<K: variant, A: any>(p: Parser<K, A>, i: u64, pos: u64, far: Far) -> Step!ParseError

A reference to production i — and the only rule that builds a node. The production's own rule matches, and its children go into one Tree(i, ..).

A labelled production that fails *without getting anywhere* reports as its label instead of as the expectations from inside it — the collapse SYMBOL_DISPLAY_NAMES performs for the LR parser, where expr/term/atom all render as "expression". It matters more here than there: under ordered choice every alternative of a failed OneOf leaves its own expectation behind, so an uncollapsed message lists the grammar's internals.

"Without getting anywhere" is the operative test. When the production failed *deeper* than it started, that deeper expectation is the useful one and the label is not applied; when it failed at its own first token, the label replaces what it expected there — but only what *this* production contributed, since the incoming far (a sibling alternative's expectations at the same position) is what the label is merged into. A transparent production (empty expect_as) never collapses anything: its insides are the message.

can_reach fn 

fn can_reach<K: variant, A: any>(p: Parser<K, A>, i: u64, pos: u64) -> bool

Whether production i could begin with the token at pos — its FIRST set asked about that token's kind and spelling.

True at end of input, where there is no token to rule anything out: a nullable production still matches there, and the cost of trying the rest is one failed token compare. can_start is conservative in the safe direction anyway, so the only thing a wrong answer here could cost is the pruning itself.

pruned fn 

fn pruned<K: variant, A: any>(p: Parser<K, A>, i: u64, pos: u64, expect_as: str, far: Far) -> Step

The Step a pruned production yields — the one its rule would have produced, without running it.

A pruned production cannot consume the token at pos, so it cannot fail any deeper than pos; that is exactly the branch of match_prod where a label replaces what the production's insides expected. So for a *labelled* production this is observationally identical to attempting it.

A transparent one has no label to record, and what it would have recorded is its insides' expectations at pos — which pruning skips over. That is a real difference and it is confined to the expected-set of an error reported at this exact position; see label_sets in ebnf.aipl for the exact version.

label_sets fn 

fn label_sets<K: variant, A: any>(prods: Production<K, A>[], firsts: First<K>[]) -> #{str}[]

The expectation labels each production would record on failing at its own first token, in grammar order — the FIRST set computed over *labels* rather than terminals, so a labelled sub-production contributes its label and a transparent one contributes its insides.

This exists so pruning is invisible. match_prod's label branch already makes a pruned *labelled* production observationally identical to an attempted one; a transparent production has no label, and what it would have recorded is exactly this. Without it, skipping a production silently drops entries from the "expected a, b, or c" set of any error reported at that position — which the driver's own tests catch, seven of them.

A fixed point for the same reason first_sets is one: a transparent production referencing another is not answerable until that one is.

These really are sets, and are spelled as sets. That also makes the fixed point's own test exact: #{str} equality is membership, so a round that reaches the same labels by a different route ends the loop instead of spinning — where deduped arrays would have compared unequal on order alone.

climb fn 

fn climb<K: variant, A: any>(p: Parser<K, A>, atom: Rule<K>, precs: Prec[], pos: u64, min_power: u64, cur: u64, far: Far) -> Step!ParseError

Precedence climbing: an atom, then any operator binding at least as tightly as min_power, whose right-hand side is climbed at one power higher (or the same power, for a right-associative level).

Each application nests *both* operands under the enclosing production's index while leaving the outermost one flat, so match_prod's own wrap completes the tree: 1 + 2 * 3 becomes (expr (expr 1) + (expr (expr 2) * (expr 3))) — one node per operand, shaped by precedence rather than a flat run the lowering would have to re-parse.

unclosed_hint fn 

fn unclosed_hint(src: str, open: Span[]) -> str

The parenthetical naming the bracket that was never closed, or the empty string when no group got that far. The span stays on the *failure*, which is where the reader has to type something; the opener is named by line because pointing at two places at once is what a single-span error cannot do.

This is the whole reason nested_in exists on the parsing side: a flat Then([Lit("("), .., Lit(")")]) fails at the close having forgotten there was an open, and reports "expected ), found end of input" a hundred lines away from the ( that caused it.
