aipl_grammar fn 

pub fn aipl_grammar() -> Grammar<AiplTok, Ast>

AIPL's grammar: the productions the driver in parse.aipl parses AIPL with, starting at program.

Split across five builder functions purely for reading — the array they concatenate to is one flat production list, and position in it is identity (a linked NamedIdx and a CTree both name a production by its index).

aipl_source fn 

pub fn aipl_source(src: str) -> str

The part of src that is AIPL: everything before the first --- section --- marker, which is where a test-case file stops being source and starts being expected output. aipl_parser::parse strips exactly this, and aipl_parse_cst parses exactly this — so a losslessness assertion is against this string, not the whole file.

aipl_parse_cst fn 

pub fn aipl_parse_cst(src: str) -> Cst!ParseError

The lossless concrete syntax tree for AIPL source src, parsed by the library against aipl_grammar().

Every byte of aipl_source(src) is under exactly one leaf. That needs the lexer's rule set read *losslessly* (keep_skipped): the compiler's own lexing skips whitespace outright, having no use for it, and a concrete tree has to be able to put it back. Nothing else needs putting back — every other byte, the braces around a template interpolation included, already sits inside some token's span.

format_aipl_ty fn 

pub fn format_aipl_ty(src: str, width: u64) -> str!ParseError

One AIPL **type**, laid out by the generated formatter.

This is the stage-4 claim, stated where it can be checked. walker.aipl lays out a type with six hand-written functions — ty, paren_ty, ty_list, base_ty, set_or_dict_ty, dict_value_ty, named_ty, type_suffixes, array_suffixes — about ninety lines of cursor-walking that mirror, by hand, productions this file already describes. Here the same layouts are four annotations on those productions plus ty_space below, and the assertions under this function are walker.aipl's own type assertions copied verbatim: same inputs, same expected strings, including the broken-list case. Both sides lex with lex_aipl, so the inputs mean the same thing to both.

What that does *not* say: the rest of AIPL is not this tractable. Statements want a hard-broken block layout that format.aipl does not have an arm for yet, and expressions want call hugging and chain breaking, which are not layout at all. The types are the honest measure of the mechanical part — and the mechanical part is most of the grammar-shaped half of the walker.

lower_aipl_ty fn 

pub fn lower_aipl_ty(src: str) -> Ty!ParseError

One AIPL **type**, lowered to the AST — the stage-5d claim for the slice that is finished, stated where it can be checked.

parse is parse_cst followed by lower, so this is the whole pipeline: the concrete tree is built and discarded, and what comes back is a Ty that means the same thing aipl_parser's build actions mean by it. The assertions below are written against show_ty's structural dump rather than against a re-rendering of the source, because the question a lowering has to answer is which way i64?[] nested, and a re-rendering gives that back either way.

lower_aipl_pattern fn 

pub fn lower_aipl_pattern(src: str) -> Pat!ParseError

One AIPL **pattern**, lowered to the AST.

Patterns are the second slice that closes over itself: nothing under pattern reaches an expression, which is why the destructuring [a, b] arm — the one pattern shape that holds expressions — belongs to match_arm rather than here.

lower_aipl_expr fn 

pub fn lower_aipl_expr(src: str) -> Expr!ParseError

One AIPL **expression**, lowered to the AST.

This is most of the language: statements lower to expressions too, and the atom production reaches blocks, match arms and patterns, so what parses here is nearly everything but a declaration. The one thing it cannot do yet is a block holding a keyword statement — that slice is next, and a block that holds one refuses rather than dropping it.

lex_lossless fn 

pub fn lex_lossless(text: str) -> LexResult<AiplTok>!ParseError

The whole rule set, read losslessly — every byte accounted for by a token or a trivia record. Lexing and parsing report failure in the same shape but not the same type, so the conversion happens once, here.

Public because the two halves are worth having apart: a caller parsing many sources prepares the grammar once (prepare) and then pays only this and parse_prepared per file. aipl_parse_cst is the one-shot convenience.

aipl_node_spans fn 

pub fn aipl_node_spans(src: str) -> u64[]!ParseError

What this grammar makes of src, in one string: empty when it parses *and* its concrete tree reconstructs the source byte for byte, and otherwise a line beginning error: (it did not parse, with the message) or lossless: (it did, but the tree lost bytes). Every interior node's *token* span, flattened to [start, end, start, end, ..].

The FFI entry the tree differential calls. Its question is whether the two grammars agree about *shape*, not just about acceptance — whether they group a + b * c the same way — and spans are how to ask it without writing a renderer for each side and diffing the output, which is most of the work of lowering, done twice. Both sides already carry a span on every node.

Token spans, not span: trivia attaches in front of the token that follows it, so a node's plain span reaches back over the whitespace before it while gazelle's spans are token-tight. Comparing the two without this is off by the leading whitespace at every node (see token_span).

Flat pairs rather than a nested shape because this crosses the FFI, where an array of numbers is the cheapest thing to marshal. A node holding no token contributes nothing — there is no span to compare.

aipl_parse_report fn 

pub fn aipl_parse_report(src: str) -> str

The FFI entry the corpus differential test calls — one crossing and one parse per file, checking both properties at once. Rejection is half the comparison: a grammar that accepts everything agrees with nothing.

aipl_parses fn 

pub fn aipl_parses(src: str) -> bool

Whether src parses as AIPL. The FFI entry the corpus differential test calls: it compares this against aipl_parser::parse succeeding, file by file, over every .aipl in the repository.

same_bindings fn

lower_pattern fn 

fn lower_pattern(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

pattern — the seven alternatives, told apart by the first token they matched.

A literal is what its delimiter says it is; everything else opens with an identifier or none, after which the payload child (present or not) and the . ty_space fn 

fn ty_space(l: str, r: str) -> bool

The spacing rule for the productions annotated so far: spaces around ->, a space after the : of a dict type, and nothing anywhere else.

Everything else a reader would call spacing in a type is a list separating its items, which the Wrap layouts do, or a suffix written against its core, which Tight does. That is the shape the rule takes in a real language: a handful of tokens that want air, and silence for the rest.

p fn 

fn p(name: str, rule: Rule<AiplTok>) -> Production<AiplTok, Ast>

One production with the placeholder lowering, laid out Inline. A production that has been given a real one says so with .with_build(..); until every one has, keep is what the rest pass.

Inline is the default in the same sense expect_as: "" is: it is what a production says when it has nothing particular to say. A production whose layout matters names it through pw or pt below.

nest fn 

fn nest(open: str, body: Rule<AiplTok>, close: str, style: ListStyle) -> Rule<AiplTok>

A bracketed group: open, whatever it holds, close, and how that lays out. Shorter than the Many it builds, because a grammar this size writes a lot of them and the four arguments matter more than the spelling.

min=1, max=1 is "exactly one thing in brackets" — the body is a single rule, not a list. The layout still is a list's, and style says so outright: what these groups hold is usually a production that is itself a list ((args)), and the Many holding it has no separator of its own to read one off.

nest2 fn 

fn nest2(open1: str, open2: str, body: Rule<AiplTok>, close: str, style: ListStyle) -> Rule<AiplTok>

The same for a bracket written as two tokens (#{), which is a bracket like any other — the group says where it ends, so nothing downstream counts tokens to find out.

only fn 

fn only(open: str, body: Rule<AiplTok>, close: str) -> Rule<AiplTok>

A bracket pair holding exactly one thing — a block's braces, a condition's parentheses, a grouping paren. nest without a stated style: min=1, max=1 is what says it is not a list, and desugar reads that back as a group laid out inline rather than broken at a width. It is still a group, so an unclosed one is reported against the token that opened it.

A comma-separated list that takes no trailing comma when it breaks, which most of AIPL's bracketed positions want.

loose fn

braced fn

The same, in braces that read as words and so take inner spaces while flat: { a, b } against (a, b).

keep fn 

fn keep(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

What a production with no lowering yet passes. Build has no payload-free arm to mean "nothing to lower", so Ignored — declared in ast.aipl beside the AST cases that are replacing it one production at a time — stands in.

with_build fn 

fn with_build(self: Production<AiplTok, Ast>, build: Build<Ast>) -> Production<AiplTok, Ast>

The production p/pl/pt built, given a lowering. Attaching it here rather than as a fourth argument to each of the three keeps the production lists reading as one column of shapes, and keeps the shape helpers from multiplying by the two things a production says that are not its rule.

It takes the wrapped Build, not the function — a function value may be *called* through a parameter but not stored into a field or a constructor from one, so Mk has to be written at the call site where the name is still a name. See the constraint list in PARSER_LIBRARY.md.

It disappears with keep: once every production names a lowering, build is no more optional than rule is.

wrong_kind fn 

fn wrong_kind(want: str, got: Ast, span: Span) -> ParseError

What a production lowered, where something else was wanted. Every one of these is a lowering bug rather than a bad program — the grammar guarantees the shape — so the message names both sides and leaves it there.

as_ty fn 

fn as_ty(v: Ast, span: Span) -> Ty!ParseError

The projections out of Ast, one per case a build reads. Each is an if let rather than a match: a match on a fourteen-case variant has to spell every other case out, once per projection, and what they all do is the same refusal.

kid fn 

fn kid(kids: Ast[], i: u64, span: Span) -> Ast!ParseError

Child i, or a refusal. A build reads its children positionally, and a missing one means the rule and the lowering disagree about the production's shape — the failure mode this exists to name.

tuple_ty fn 

fn tuple_ty(ts: Ty[], example: str, span: Span) -> Ty!ParseError

A parenthesized list used as a tuple. Gazelle validates the arity in its build action rather than in the grammar, for the reason this one does: (A) and () are parenthesized lists that parse, and only what follows them says whether they were meant as a tuple or as a function type's parameters. example completes the advice with the suffix that was actually written.

named_ty fn

What a bare type identifier names: a primitive, the anonymous bound any, or something declared elsewhere — a struct, a variant, a type parameter, Error. The same three-way decision BaseTy::Named's action makes, in the same order.

lower_ty fn 

fn lower_ty(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

ty — the eight alternatives, told apart by their left child's Ast case and by the tokens this node matched itself.

!E is the one alternative with no left operand at all: a result whose ok side is unit, which is why a single child under a ! lowers to TyResult(TyUnit, ..).

lower_ty_parens fn 

fn lower_ty_parens(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

ty_parens — the parenthesized list every (-led type form opens with. It is the one production whose value is a list rather than a type, and that is what lower_ty reads to tell those forms from the unparenthesized ones.

lower_base_ty fn 

fn lower_base_ty(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

base_ty — a core and its ?/[] suffix run, applied in source order, so i64?[] is an array of optionals and i64[]? an optional array. The suffixes are literals inside a Many and so are this node's own tokens; [ contributes nothing and ] is what closes an array suffix.

lower_ty_core fn 

fn lower_ty_core(src: str, node: Cst, kids: Ast[]) -> Ast!ParseError

ty_core — #{K: V}, #{T}, Name<A, B> and a bare Name. The # is what separates the two brace forms from the two name forms, and after that the child count says which of each pair matched.

Case<V> borrows the generic-application syntax but is a type of its own: one case of a variant, carrying no payload. Spelled out here for the reason gazelle spells it out — so nothing downstream has to know that one base name is special.
