aipl_grammar fn 

pub fn aipl_grammar() -> Grammar<AiplTok, Ast>

AIPL's grammar: the productions the driver in parse.aipl parses AIPL with, starting at program.

Split across five builder functions purely for reading — the array they concatenate to is one flat production list, and position in it is identity (a linked NamedIdx and a CTree both name a production by its index).

aipl_source fn 

pub fn aipl_source(src: str) -> str

The part of src that is AIPL: everything before the first --- section --- marker, which is where a test-case file stops being source and starts being expected output. aipl_parser::parse strips exactly this, and aipl_parse_cst parses exactly this — so a losslessness assertion is against this string, not the whole file.

aipl_parse_cst fn 

pub fn aipl_parse_cst(src: str) -> Cst!ParseError

The lossless concrete syntax tree for AIPL source src, parsed by the library against aipl_grammar().

Every byte of aipl_source(src) is under exactly one leaf. That needs the lexer's rule set read *losslessly* (keep_skipped): the compiler's own lexing skips whitespace outright, having no use for it, and a concrete tree has to be able to put it back. Nothing else needs putting back — every other byte, the braces around a template interpolation included, already sits inside some token's span.

format_aipl_ty fn 

pub fn format_aipl_ty(src: str, width: u64) -> str!ParseError

One AIPL **type**, laid out by the generated formatter.

This is the stage-4 claim, stated where it can be checked. walker.aipl lays out a type with six hand-written functions — ty, paren_ty, ty_list, base_ty, set_or_dict_ty, dict_value_ty, named_ty, type_suffixes, array_suffixes — about ninety lines of cursor-walking that mirror, by hand, productions this file already describes. Here the same layouts are four annotations on those productions plus ty_space below, and the assertions under this function are walker.aipl's own type assertions copied verbatim: same inputs, same expected strings, including the broken-list case. Both sides lex with lex_aipl, so the inputs mean the same thing to both.

What that does *not* say: the rest of AIPL is not this tractable. Statements want a hard-broken block layout that format.aipl does not have an arm for yet, and expressions want call hugging and chain breaking, which are not layout at all. The types are the honest measure of the mechanical part — and the mechanical part is most of the grammar-shaped half of the walker.

lex_lossless fn 

pub fn lex_lossless(text: str) -> LexResult<AiplTok>!ParseError

The whole rule set, read losslessly — every byte accounted for by a token or a trivia record. Lexing and parsing report failure in the same shape but not the same type, so the conversion happens once, here.

Public because the two halves are worth having apart: a caller parsing many sources prepares the grammar once (prepare) and then pays only this and parse_prepared per file. aipl_parse_cst is the one-shot convenience.

aipl_parse_report fn 

pub fn aipl_parse_report(src: str) -> str

What this grammar makes of src, in one string: empty when it parses *and* its concrete tree reconstructs the source byte for byte, and otherwise a line beginning error: (it did not parse, with the message) or lossless: (it did, but the tree lost bytes).

The FFI entry the corpus differential test calls — one crossing and one parse per file, checking both properties at once. Rejection is half the comparison: a grammar that accepts everything agrees with nothing.

aipl_parses fn 

pub fn aipl_parses(src: str) -> bool

Whether src parses as AIPL. The FFI entry the corpus differential test calls: it compares this against aipl_parser::parse succeeding, file by file, over every .aipl in the repository.

ty_space fn 

fn ty_space(l: str, r: str) -> bool

The spacing rule for the productions annotated so far: spaces around ->, a space after the : of a dict type, and nothing anywhere else.

Everything else a reader would call spacing in a type is a list separating its items, which the Wrap layouts do, or a suffix written against its core, which Tight does. That is the shape the rule takes in a real language: a handful of tokens that want air, and silence for the rest.

p fn 

fn p(name: str, rule: Rule<AiplTok>) -> Production<AiplTok, Ast>

One production with the trivial lowering, laid out Inline. Nothing here builds an AST — the tree is the product — so every production shares one build.

Inline is the default in the same sense expect_as: "" is: it is what a production says when it has nothing particular to say. A production whose layout matters names it through pw or pt below.

pl fn 

fn pl(name: str, rule: Rule<AiplTok>, expect_as: str) -> Production<AiplTok, Ast>

The same, labelled: what an error blames when this production fails having matched nothing. The reified form of the LR parser's SYMBOL_DISPLAY_NAMES, which is why only the handful of rules a reader would name are labelled and every plumbing rule stays transparent.

nest fn 

fn nest(open: str, body: Rule<AiplTok>, close: str, style: ListStyle) -> Rule<AiplTok>

A bracketed group: open, whatever it holds, close, and how that lays out. Shorter than the Many it builds, because a grammar this size writes a lot of them and the four arguments matter more than the spelling.

min=1, max=1 is "exactly one thing in brackets" — the body is a single rule, not a list. The layout still is a list's, and style says so outright: what these groups hold is usually a production that is itself a list ((args)), and the Many holding it has no separator of its own to read one off.

nest2 fn 

fn nest2(open1: str, open2: str, body: Rule<AiplTok>, close: str, style: ListStyle) -> Rule<AiplTok>

The same for a bracket written as two tokens (#{), which is a bracket like any other — the group says where it ends, so nothing downstream counts tokens to find out.

only fn 

fn only(open: str, body: Rule<AiplTok>, close: str) -> Rule<AiplTok>

A bracket pair holding exactly one thing — a block's braces, a condition's parentheses, a grouping paren. nest without a stated style: min=1, max=1 is what says it is not a list, and desugar reads that back as a group laid out inline rather than broken at a width. It is still a group, so an unclosed one is reported against the token that opened it.

strict fn 

fn strict() -> ListStyle

A comma-separated list that takes no trailing comma when it breaks, which most of AIPL's bracketed positions want.

loose fn 

fn loose() -> ListStyle

A comma-separated list that gains a trailing comma once it breaks — argument lists, array literals, struct literals.

braced fn 

fn braced() -> ListStyle

The same, in braces that read as words and so take inner spaces while flat: { a, b } against (a, b).
