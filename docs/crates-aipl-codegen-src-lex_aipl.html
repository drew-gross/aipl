StrStyle variant pub 

variant StrStyle

Every string literal — "...", """...""", and an interpolation-free ... / ... template — lexes to one StrLit (below) carrying its *decoded* value and the delimiter it was written with, this StrStyle. A Triple/TripleBacktick literal's value is de-dented in the emit; a Quoted/Backtick one is single-line and only escape-decoded. The style lets the autoformatter recover the original spelling from the value.

doc_text fn 

fn doc_text(line: str) -> AiplTok

Identifier character classes: the chars that may start an identifier (letters and _) and those that may continue one (adds digits). A keyword rule uses the continue class as its boundary, so if doesn't bite the front off iffy (see kw), and the identifier rule uses both (see aipl_rules). A doc comment's text: the line past its #, with one optional space of separation removed. # text and #text carry the same text, and a bare # an empty line — so a doc block's blank lines survive as blank lines.

kw fn 

fn kw(spelling: str, kind: AiplTok, scope: str) -> TokenRule<AiplTok>

One keyword/constant rule: match the exact spelling at an identifier boundary (so fn/true don't split fnord/trueish) and emit the fixed kind. Every keyword and constant is a single kw call in aipl_rules, so the spelling and its AiplTok arm are named together — no spelling→arm match to keep in sync with a separate spelling list.

op fn 

fn op(spelling: str, kind: AiplTok, scope: str) -> TokenRule<AiplTok>

One operator/punctuation rule: match the exact spelling (no identifier boundary) and emit the fixed kind. Each op is one rule matching one spelling, and rules are first-match-wins — so aipl_rules lists the op rules longest spelling first (== before =) to keep maximal munch.

tpl_kind fn 

fn tpl_kind(text: str, seg: Seg) -> AiplTok

The OfSeg emit for the ... template rule: the Template matcher hands each text segment's *raw* text plus its position (Plain for an interpolation-free literal, else Head/Middle/Tail), and this maps each to its own AiplTok arm — decoding the segment's escapes ( \ /\{/\n/… as in the escapes set below) with unescape, exactly as the "..." emit does. An interpolation-free template (Plain) folds into StrLit (with Backtick style) — the same token any other string literal produces — while a template *with* interpolations keeps distinct TemplateHead/Mid/Tail kinds.

dedent_segments fn 

fn dedent_segments(segs: str[]) -> str[]

The segment finalizer for the raw-template rule (the Template matcher's finalize): de-dent the whole literal's text segments *together*, so the common indent is computed across the entire template — just like a """ raw string. The segments are joined by { (which can't occur inside a raw segment, since a { always opens an interpolation), de-dented as one block via the dogfooded process_raw_string, then split back. A no-interpolation raw template is the one-segment case (de-dent that single segment).

raw_tpl_kind fn 

fn raw_tpl_kind(text: str, seg: Seg) -> AiplTok

The OfSeg emit for the ... raw-template rule: like tpl_kind, but the delimiter scans verbatim (empty escapes), so the segment text isn't escape-decoded — a lone / inside is content. The segments arrive already de-dented (by dedent_segments, the rule's finalize), so this just wraps them: an interpolation-free raw template (Plain) folds into StrLit with TripleBacktick style, and an interpolated one keeps distinct RawTemplate* kinds.

int_lit fn 

fn int_lit(text: str) -> AiplTok!str

Build an IntLit from a matched integer run (an optional leading - then digits). The Int matcher only claims the run; parsing is the caller's job, so this parses it — sign and all — with the int_parse builtin and, as a fallible Try emit, reports an i64 overflow as an error message — the library attaches the literal's span. Parsing policy lives here, in the consumer, not the library. int_parse's none becomes that message via value_or_err, and ? hands it straight back as this emit's err.

char_lit_emit fn 

fn char_lit_emit(text: str) -> AiplTok!str

Decode and validate a single-quote literal. This is where AIPL *defines* what a char literal is: the Delimited("'", ..) matcher (the same escape-aware scan "..." strings use) just hands over the un-decoded text between the quotes, and this emit unescapes it and requires exactly one char — so an empty ('') or multi-char ('ab', 'multiple') literal is a hard error. As a Try emit the library pairs the message with the *whole* literal's span, so the caret underlines the entire bad token. Unknown escapes and unterminated literals are caught earlier, by the matcher's own scan (its escapes set).

s_keyword fn 

fn s_keyword() -> str

The AIPL rule set. Order is priority (the first matching rule wins): skipped whitespace and recorded comments/markers first; then every keyword and constant (each its own kw rule) before the identifier rule, so fn isn't swallowed as a Name; then numbers, strings, char literals, and templates; and finally the operator/punctuation rules — each spelling its own op rule, listed longest first so first-match-wins still yields maximal munch (== before =), since separate rules don't get Exact's automatic longest-match. The TextMate scopes AIPL's tokens are painted with, named once here so the rule table below reads as spelling/kind/scope triples and editors/vscode/syntaxes/aipl.tmLanguage.json — generated from this table by highlight_aipl.aipl — cannot disagree with it. These are TextMate's conventional names, which is what lets an editor theme colour AIPL without knowing anything about AIPL.

atok fn 

fn atok(src: str, kind: AiplTok, span: Span) -> Token<AiplTok>

Lex AIPL source into typed AiplTok tokens (plus the trivia side-channel: comments and #[allow] markers; whitespace is skipped outright). This is the compiler's dogfood entry (see DOGFOOD_ENTRIES): the Rust side calls it via the FFI and mirrors the result into its own token types. Test shorthand: the expected token at span in src. Like lexer.aipl's tok, the text is sliced from the same source the lexer was given, so an expectation cannot claim text the source does not hold at that span.

lex_aipl_tokens fn pub 

pub fn lex_aipl_tokens(src: str) -> Token<AiplTok>[]!LexError

lex_aipl_tokens is the FFI entry the Rust tests/lexer_dogfood.rs calls to compare this AIPL lexer against the compiler's hand-written Rust lexer over the test corpus. It hands back the *actual* token array — Token<AiplTok>[], each token carrying its typed kind and span — which crosses the embedding FFI directly (an array of structs whose fields are themselves a variant and a struct). The Rust side coarsens each kind to a category and diffs spans, building a burn-down list of the remaining divergences; nothing here is used to compile. trivia is dropped: the differential dump compares only the emitted token stream (the Rust lexer's dump has no comment/marker lines to compare the side-channel against).

lex_aipl_stripped fn pub 

pub fn lex_aipl_stripped(src: str) -> LexResult<AiplTok>!LexError

Strip trailing --- section --- cases-harness blocks, then lex. The highlighter and the parser both want AIPL source with those blocks removed, and both strip_test_sections and lex_aipl are dogfooded — composing them here keeps the whole strip-then-lex a single FFI crossing instead of one per step. Spans are unchanged: strip_test_sections returns a byte-prefix of src, so every kept token's span still indexes the original source.
