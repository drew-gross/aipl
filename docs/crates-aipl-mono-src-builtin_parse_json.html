The AIPL implementation of the parse_json builtin. The loader names this function by the canonical name __builtin_parse_json (see aipl_syntax::aipl_builtins). The file also defines Json and Member, and Json's cases, which a program imports from builtins beside parse_json.

It is the parser library's end-to-end JSON target: a lexer rule table, eight productions and the lowering that builds a Json, driven by parse. The library lives in aipl-codegen/src/, and a program that calls parse_json loads the part of it this file imports. grammar_json.aipl holds what is built on this grammar besides parsing: printing, formatting, and the tests of the grammar as data.

No lint. Nothing is being reimplemented: there is no longhand to match.

Numbers stay text. Number carries the source spelling rather than a parsed value, because JSON's number syntax is wider than any one AIPL type (an arbitrary-precision integer is legal JSON), so what a number means is the consumer's policy, exactly as it is for the lexer's Int/Float, which hand over their digits unparsed for the same reason.

member lowers to a one-member object. Build<A> pins one A for every production in a grammar, so the member production — whose natural result is a key/value pair, not a JSON value — has to lower to a Json too. It lowers to the object holding just that member, and the object production joins the members of its children, so Json has no case that only means "a member".

parse_json fn 

pub fn parse_json(self: str) -> Json!str

The JSON self denotes: ok(json), or err(message) saying what was expected, what was found and where (the message ends (at byte N)).

Strict JSON: no trailing commas, no comments, and one value per document. Numbers arrive as their source spelling (Number("1e9")), since JSON's number syntax is wider than any one AIPL type — reading one is the consumer's policy (int_parse). Strings are decoded for their escapes.

json_rules fn 

fn json_rules() -> TokenRule<JsonTok>[]

Whitespace is recorded as trivia rather than skipped, so the concrete tree covers every byte of the source and reconstructs it exactly. JSON has no comments, so trivia is whitespace and nothing else.

Rule order carries two decisions. Float sits ahead of Int because a bare digit run doesn't match Float and 1.5 would otherwise lex as 1 then a stray .. And Exact("-") sits ahead of both, which makes every - its own token and Int unsigned — so the sign is the grammar's business (Maybe(Lit("-")) in number), one place, rather than split between a sign the lexer swallowed and one it didn't.
