The AIPL implementation of the filter_map_reduce builtin. Monomorphization registers this function under the canonical name __builtin_filter_map_reduce (see AIPL_BUILTIN_SOURCES in lib.rs), so a user's xs.filter_map_reduce(keep, f, step) resolves through the ordinary generic / higher-order machinery — the in-file name is only for this file's own tests, which read exactly like user code.

It is what xs.filter(keep).map(f).<reduction>() means, in one pass and with no array built at all: filter would allocate the survivors and map their mapped values, for the reduction to walk once and drop. It is map_reduce (see builtin_map_reduce.aipl) over only the elements keep accepts. Written by the compiler's operation-fusion pass for those chains (see chain_fusions in aipl-mono, and Callee::reduction_step, where the reductions are named); also callable directly.

filter_map_reduce fn 

pub fn filter_map_reduce<T: any, U: any>(self: T[], keep: (T) -> bool, f: (T) -> U, step: (U, U) -> U) -> U?

The elements keep accepts, each mapped by f, combined left to right with step: for the survivors [a, b, c], some(step(step(f(a), f(b)), f(c))). The first mapped survivor seeds the result, so step is never called on fewer than two; when nothing survives — an empty receiver, or a keep that accepts none — it is none.

keep then f run per element, in order, interleaved with step and with the next element's keep — which no one can tell apart unless one of them does something, and the fusion that writes this call refuses when any does.
