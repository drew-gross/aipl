The AIPL implementation of the set_map builtin. Monomorphization registers this function under the canonical name __builtin_set_map (see AIPL_BUILTIN_SOURCES in lib.rs), so a user's s.set_map(f) resolves through the ordinary generic / higher-order machinery — the in-file name set_map is only for this file's own tests, which read exactly like user code.

No lint steers a hand-written loop here, because the shape a lint could match is not the shape this replaces. push_loop_pipeline already flags mut out = []; for (let x : s) { set out.push(f(x)); }, and that loop builds an array; the loop set_map replaces builds a set, which means a mut out = #{} seed and a union per element — and union_loop_union_all owns that shape, pointing at union_all. Telling the two apart needs the element type of the mapping, which no lint has: they run in aipl-syntax, two passes before any type is known.

set_map fn 

pub fn set_map<T: any, U: any>(self: #{T}, f: (T) -> U) -> #{U}

Every element of self through f, as a set.

This is map for a set: a set in, a set out. Which means the result can be smaller than the receiver — an f sending two elements to the same answer yields one element, because that is what a set is. That is the honest reason this is its own builtin rather than another receiver map accepts: map says "one element out per element in", and over a set it cannot keep that promise, so the set version is spelled differently and a reader sees which one they are looking at.

Callable as a method (chars.set_map(escape)). The receiver is a set of any order; the result is always unordered, because f changes the very values an order would be over. Ask for one explicitly when you want it — s.to_array().map(f).to_set() with the binding annotated #<{U} — so the re-sorting is written down rather than inferred.

See map for the array and optional forms.
