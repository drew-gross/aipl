crates/aipl-codegen/src/grammar_json.aipl

What is built on the JSON grammar besides parsing it: printing, formatting, and the tests of the grammar as data. The grammar, the lexer rules, the lowering and parse_json itself are the parse_json builtin (aipl-mono/src/builtin_parse_json.aipl), which programs import; this file imports them the way the parser library's other consumers do.

JSON is the library's second end-to-end target, and the one that adds everything S-expressions deliberately left out — several terminal classes rather than one, a separated Many with a trailing-comma rule, an OneOf across six alternatives, and a heterogeneous AST. Still no precedence; that arrives with the calculator in grammar_calc.aipl.

render_json fn 

pub fn render_json(self: Json) -> str

self printed back as JSON source, in one canonical compact spelling: no spaces, no trailing separators, strings escaped.

Round-trips with parse_json — parse_json(render_json(v)) == v for every v a parse produced — which is what makes the pair a usable end-to-end check of the library.

The whole of JSON's layout is the eight annotations on the grammar above plus json_space below. There is no second walker over JSON's syntax, and adding a ninth production would need no more than a ninth annotation — which is the claim this stage exists to make good on. Key order is part of that claim: the members of every object come out sorted, and the only place that is said is sorted=true on the object's Many.

json_space fn 

fn json_space(l: str, r: str) -> bool

JSON's whole spacing rule: a space after the : of a member, and nowhere else. Everything else that looks like spacing — between members, inside braces — is a list breaking or not breaking, which the layouts decide.
