mtg_metagame workarounds:
  no binary file read / gzip: load_metagame shells out to `gzip -dc` via execute_program
  no JSON library a project can use (grammar_json.aipl is compiler-internal): projects/mtg_metagame/json.aipl is hand-written
  json.aipl: `\u` escapes (and \b \f) refused; no char-from-code-point, and `"\u{8}"` isn't a string escape
  `insert_key` is internal, so counting by key means to_dict for positions + an array with try_set; a dict-update/`entry` API would do
  `sort_by` is a quadratic insertion sort; no native sort by key/comparator (card_counts sorts ~500-3000 entries with it)
  `to_array` needs an ordered set: `let s: #<{str} = xs.to_set()` just to get sorted unique values (a `sorted_unique`/`distinct` builtin?)
  no `break` in loops: `while (true)` + `return` in a match arm, with an unreachable trailing `err("unreachable")`
  `while (let some(c) = ..)` doesn't parse
  lambdas need a braced body even for a struct literal: `|n| { Card { .. } }`
  `ok(Struct { f: x? })` is required: a bare field-list body can't be a `T!E` return, and `?` on `T?` in a `T!E` fn needs value_or_err
  maybe: `fn f(self: Json) -> Card!str ok({ name: .., count: .. })` as the struct-body shorthand for a `T!E` return (the `ok(..)` stays written, the `Card { }` is dropped); Drew is not convinced yet, and no implicit ok-wrapping
  `str[i]` is a byte (invalid UTF-8 chars show as �); fine for scanning, but no char iteration by code point

handoff:
  `let (Parts { n }, rest) = f(xs);` (a struct pattern nested in a tuple pattern) over a generic `(Parts, A[])` fails in a generic caller: struct "__tuple$i64$i64" field "_1": expected i64, got i64[]; concrete callers work. The destructure lint steers people to this form, so the workaround is `#[allow]` on a plain `let (p, rest)` (tests/cases/tuples/destructure_generic_result.aipl)
parser library perf (builtin parse_json, 10MB: lex 0.77s / parse_cst 1.1s / lower 0.7s, vs ~1s for a hand-written parser; ~10 allocations and ~8k instructions per token):
  match_* thread a Step {kids, far: Far{3 arrays}} by value through every rule: refcount traffic on Far's arrays is ~30% of the parse
  a JSON value is value -> (array|object|..) -> group nodes: ~2-3 Tree nodes per scalar, each with its own Parts (3 allocations) in lowering
  lexer tries every rule in order per token (nine for `{`/`,`); a first-byte dispatch table per mode would skip most
  parse then lower builds the whole Cst; a lower-while-parsing path for grammars that never read the tree

language perf (from the parse_json investigation; counts are IR instructions via `aipl report`, tiny.json):
  structs with N refcounted fields cost N retains + N releases per copy (`Step{..s}` 4 inc/level; a move ~0.1): box a struct of 3+ refcounted fields behind one refcount with COW (recursive types already have the runtime). Measured: boxing Far alone via `boxed: Far? = none` took parse_cst 117M -> 83M (-29%)
  inline the refcount fast path (`rc != STATIC; rc += 1` / `rc -= 1; if zero slow path`) instead of calling aipl_arr_inc/array_dec/rec_*: ~1/3 of parse time is those calls; runtime is non-atomic; lib.rs:6375 notes opt_level=speed doesn't beat none for this reason
  loop-carried scalars (`mut` locals, hidden for-index) live in stack slots with load/store per use: `for (i, c : str)` ~59 IR instr/char, `for` over u64[] ~28/element vs ~5 ideal; use SSA variables for non-address-taken scalars
  spread `T { ..s, f: x }` from a single-use temp retains every field then releases the temp: treat the desugared `tmp.f` reads as moves (move_last_use.rs)
  `mut t = f(); set t.field++; t` forks the struct (16 retain/release pairs, ~480 instr) vs ~4 for the spread: move the dead call result into the `mut`
  `[x].repeat(n)` ~37 IR instr/element: bulk fill
  unexplained: a 2-param recursive `m(r: Rule, d) { Opt(sub) => m(sub, d) }` does one rec_inc_strong/dec_strong per node, the 1-param version none; `acc.extend(heap_array)` reallocs where `extend([i])` doesn't
floats (first landing: types, literals, + - * /, comparisons, to_str; conversions and formatting options are TODO.txt's):
  no compound float operators (`set x += 0.5;`): float_add_assign etc. are not defined, and the compound_assign lint cannot pair float_add
  `t.0.1` (nested tuple slots) lexes `0.1` as a float: write `(t.0).1`
  a variant payload holding a float is not rejected by `==` (only struct, tuple, array, optional, set, dict, result are walked)
  a file can import one `==`: with `float_equal as ==` every other comparison there is `equal(a, b)`; consider `==` choosing by operand type if this proves noisy
  no way to compare floats within a tolerance, no float literals in patterns, no float to int conversion (int to float is `to_float`)
  `wrapping_add(a, b)` on floats says "expected i64"; only the operator spelling names the float import
mtg_metagame share report:
  ties in the share order are broken by name; the original keeps first-seen order of the archetypes, which is the pickle's deck order
  the grid pads by byte length, so a non-ASCII archetype name misaligns its row
  `xs$f` takes only a name, so `xs.map(|x| { .. })` stands in wherever a lambda is wanted (no `xs$(|x| ..)`)
  a `let` closure cannot be called by name or used as `xs$name()`: test helpers became `fn`s
render (floats):
  `render` is for floats only (its body writes a float, and a body is compiled for every instance), so `render(7)` is a compile error rather than `to_str`'s "7"; the other options TODO.txt lists (leading +, exponent form) are more keywords on it
  an integer literal that does not fit an optional keyword's type (`render(x, digits=-3)`, `digits?: u64 = none`) reports `binding "$ceq5_$inl2_wanted": expected u64, got i64`, an inlined binding's name, instead of "integer literal -3 does not fit in u64"
